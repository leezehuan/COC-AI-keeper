# coc-lite 初学者学习指南

> 面向 **Agent 初学者** 和 **Web 初学者** 的项目理解文档。  
> 目标不是只告诉你"代码在哪里"，而是帮助你理解：浏览器里的一个按钮点击，如何一路变成后端的一次多 Agent 守秘人回合，最后又如何回到页面上显示为叙事、选项、线索、物品和状态变化。

## 0. 这份文档适合谁

如果你符合下面任意一种情况，这份文档都适合从头看：

- **你会一点前端，但不熟悉后端**：你可以重点看 Web 请求链路、FastAPI、接口返回结构。
- **你会一点 Python，但不熟悉 React**：你可以重点看 `App.tsx`、`api.ts`、组件状态和流式响应。
- **你知道大模型，但不熟悉 Agent 架构**：你可以重点看 `KeeperSupervisor`、5 个专业 Agent、`AgentMessage` 信封。
- **你想改造项目**：你可以看"常见修改任务应该改哪里"和"调试路线"。

阅读前建议先知道以下最基础概念：

- **浏览器**：运行 React 前端页面。
- **HTTP API**：前端通过 URL 请求后端，例如 `/coc/api/sessions`。
- **JSON**：前后端交换数据的主要格式。
- **数据库**：PostgreSQL 保存长期数据，例如角色、会话、回合日志。
- **向量数据库**：Chroma 保存文本向量，用来做相似检索，也就是 RAG。
- **LLM**：大语言模型，用来理解玩家输入、生成守秘人叙事。
- **Agent**：一个专注于特定任务的智能模块，接收输入、执行逻辑、返回输出。
- **Supervisor**：调度多个 Agent 的协调器，负责组装输入、路由输出、控制修复循环。

| 术语 | 全称 | 一句话解释 |
|---|---|---|
| LLM | Large Language Model | 大语言模型，如 GPT-4、千问。本项目用它理解玩家输入、生成叙事 |
| RAG | Retrieval-Augmented Generation | 检索增强生成：先从资料库搜相关内容，再让 LLM 基于这些内容回答 |

| Embedding | — | 文本向量化：把一段文字变成一串数字，用于相似度搜索 |
| Chroma / ChromaDB | — | 向量数据库，存储和检索文本向量 |
| NDJSON | Newline Delimited JSON | 一行一个 JSON，用于流式传输：后端边生成边发送，前端边接收边显示 |
| MQE | Multi-Query Expansion | 多查询扩展：用 LLM 把用户问题改写成多个不同角度的问题，提高检索命中率 |

## 1. 先用一句话理解本项目

`coc-lite` 是一个网页化的《克苏鲁的呼唤》AI 守秘人原型。

玩家在浏览器里输入行动，例如：

```text
我划向北岸码头，检查码头附近有没有脚印。
```

前端会把这句话发送给后端。后端的 `KeeperSupervisor` 会调度 5 个专业 Agent 执行一整套流程：

```text
ContextAgent  → 加载会话状态、解析意图、RAG 检索
PlannerAgent  → 生成回合计划、校验白名单
ExecutorAgent → 执行 Skill、规则检定、综合裁定
NarratorAgent → 生成守秘人叙事、状态增量、选项
GuardAgent    → 确定性校验、Reflection 自检、防剧透清洗
```

如果 GuardAgent 判定需要修复，Supervisor 会进入修复循环（最多 2 次），修复后重新校验。最终落库并返回前端。

这条链路就是本项目最重要的主线。

## 4. 🔥 一回合完整走读（强烈推荐先看这个）

> 用一句具体的玩家输入，逐步追踪数据在系统中的完整旅程。  
> 读完这一节，你就能把代码里的每个函数和"玩家看到的东西"对应起来。

### 玩家输入

```
我划向北岸码头，检查码头附近有没有脚印。
```

### 第 1 步：前端发送请求

`App.tsx` 的 `send()` 函数把这句话发给后端：

```
POST /coc/api/sessions/{session_id}/actions/stream
Body: {"message": "我划向北岸码头，检查码头附近有没有脚印。"}
```

### 第 2 步：后端 API 接收

`api.py` 的 `submit_action_stream()` 收到请求，调用：

```python
result = get_agent().run_turn(db, session_id, "我划向北岸码头，检查码头附近有没有脚印。")
```

### 第 3 步：ContextAgent — 理解玩家想干什么

**输入**：玩家原始文本 + 数据库会话状态

**做了什么**：
1. 从 PostgreSQL 查出当前会话（地点="波浪起伏的水面"，场景="导入"）
2. 用 LLM 解析意图 → `{action_type: "移动", target: "北岸码头", skill: "导航"}`
3. 从 Chroma 检索"北岸码头"相关的剧本片段、实体、线索

**输出**：一个装满数据的 AgentMessage，包含意图、上下文、检索结果

### 第 4 步：PlannerAgent — 决定怎么处理

**输入**：ContextAgent 的输出（意图 + 上下文）

**做了什么**：
1. LLM 生成计划 → `{action_type: "移动", allowed_skills: ["move"], allowed_tools: ["ContextSearchTool", "SceneAffordanceTool"]}`
2. 校验白名单：确认 "move" Skill 和这些 Tool 都存在
3. 判断不需要追问（玩家意图清晰）

**输出**：回合计划 `turn_plan`

### 第 5 步：ExecutorAgent — 实际执行

**输入**：计划 + 角色数据 + 检索结果

**做了什么**：
1. 执行 `move` Skill → 调用 ContextSearchTool 检索新地点信息 → 调用 SceneAffordanceTool 获取可交互对象
2. 规则裁定：移动通常不需要技能检定，`needs_roll=False`
3. 不需要掷骰子

**输出**：执行结果（Tool 观察列表、裁定结果）

### 第 6 步：NarratorAgent — 把结果变成故事

**输入**：执行结果 + 上下文

**做了什么**：
1. LLM 生成叙事文本：
   > 你用力划动船桨，小舟在暗涌中颠簸着靠近北岸。码头腐朽的木板在月光下泛着惨白的光。你跳上码头，蹲下身仔细查看——潮湿的木板上果然有几道泥泞的脚印，从码头边缘一直延伸到通往灯塔小屋的小径……
2. 生成选项：`["追踪脚印方向", "检查脚印细节", "观察码头周围", "前往灯塔小屋", "自定义行动"]`
3. 构建状态增量：`{location: "北岸码头", scene: "北岸码头", time_cost_minutes: 5}`

**输出**：叙事文本 + 选项 + 状态增量

### 第 7 步：GuardAgent — 最后一道安全检查

**输入**：NarratorAgent 的全部输出

**做了什么**：
1. 确定性校验：`time_cost_minutes=5` 在 0-120 范围内 ✓，`location` 在白名单中 ✓
2. Reflection 自检：LLM 审查叙事是否剧透、是否矛盾 → 通过
3. 防剧透清洗：叙事中没有未发现的秘密术语 → 无需清洗

**输出**：`needs_repair=False`，校验通过

### 第 8 步：Supervisor 落库

GuardAgent 判定通过，Supervisor 执行 `_commit_state()`：
- 更新 `session.current_location` = "北岸码头"
- 更新 `session.current_scene` = "北岸码头"
- 推进游戏时间 +5 分钟
- 保存 TurnLog（玩家输入、意图、叙事、骰点等完整记录）
- 将本回合记忆写入 Chroma

### 第 9 步：返回前端

后端通过 NDJSON 流式返回：

```json
{"type":"start"}
{"type":"chunk","content":"你用力划动船桨，小舟在暗涌中颠簸着靠近北岸……"}
{"type":"chunk","content":"码头腐朽的木板在月光下泛着惨白的光……"}
{"type":"final","response":{"narration":"...","options":["追踪脚印方向",...],"session":{...}}}
```

前端收到 `chunk` 就追加到守秘人消息，收到 `final` 就刷新整个页面状态。

### 数据流总结

```
玩家输入文本
  → ContextAgent: 文本 → 结构化意图 + 检索结果
    → PlannerAgent: 意图 → 执行计划
      → ExecutorAgent: 计划 → 执行结果 + 检定数据
        → NarratorAgent: 结果 → 叙事文本 + 选项 + 状态增量
          → GuardAgent: 全部输出 → 校验通过/需修复
            → Supervisor: 落库 → 返回前端
```

## 5. Web 初学者先看：一次页面操作发生了什么

以“玩家输入行动并发送”为例。

### 5.1 页面上发生的事

文件：`frontend/src/App.tsx`

用户在输入框中输入内容，然后点击发送。核心函数是：

```text
send(message)
```

它做了几件事：

1. 去掉输入前后的空格。
2. 检查当前是否有会话、是否正在忙。
3. 把玩家消息追加到 `messages`。
4. 再追加一条空的守秘人消息。
5. 调用 `api.streamAction(...)`。
6. 接收后端流式返回的事件。
7. 不断把 `chunk` 事件追加到最后一条守秘人消息。
8. 收到 `final` 事件后，刷新完整会话状态、选项、线索、物品栏等。
9. 如果收到 `image` 事件，把生成好的配图挂到当前守秘人消息上。

### 5.2 为什么先追加一条空的守秘人消息

前端想实现“守秘人正在逐段讲述”的效果。

所以它不是等后端全部完成后再显示，而是：

```text
玩家消息：我检查灯塔门口。
守秘人消息：
```

然后后端每返回一小段文字，就把这段文字拼到最后一条守秘人消息上。

最终可能变成：

```text
玩家消息：我检查灯塔门口。
守秘人消息：你踩着湿滑的石阶靠近灯塔门口，木门在风中微微震动……
```

### 5.3 前端主要状态变量

文件：`frontend/src/App.tsx`

| 状态 | 类型直觉 | 作用 |
|---|---|---|
| `characters` | 角色列表 | 后端返回的预设调查员 |
| `savedSessions` | 会话列表 | 历史存档 |
| `selectedCharacter` | 字符串 ID | 当前选择的角色 |
| `session` | 当前会话对象 | 页面右侧状态栏主要数据来源 |
| `messages` | 聊天消息数组 | 中间聊天区展示内容 |

### 5.5 什么是 NDJSON 流式响应

普通 JSON 响应一般是这样：

```json
{
  "narration": "完整的一大段叙事文本"
}
```

前端必须等整个响应结束，才能解析它。

NDJSON 是“一行一个 JSON”：

```json
{"type":"start"}
{"type":"chunk","content":"你靠近灯塔门口，"}
{"type":"chunk","content":"潮湿的木门发出低沉声响。"}
{"type":"debug","event":{"phase":"agent_node","name":"ContextAgent","status":"start","message":"ContextAgent 开始加载状态与检索。"}}
{"type":"debug","event":{"phase":"agent_node","name":"ContextAgent","status":"success","message":"ContextAgent 完成。"}}
{"type":"image","url":"https://...","turnId":"...","metadata":{...}}
{"type":"final","response":{...完整结果...}}
```

好处是：

- 后端可以边生成边返回。
- 前端可以边收到边显示。
- 调试事件可以实时推送。
- 用户感觉系统响应更快。

本项目的 `streamRequest` 会不断读取后端数据，把每一行 JSON 解析成事件，再交给 `App.tsx` 处理。

### 6.3 API 如何调用 Agent

主回合接口中有一行非常关键：

```text
result = get_agent().run_turn(db, session_id, payload.message)
```

当前版本里，`get_agent()` 直接返回 `KeeperSupervisor` 单例。也就是说，API 层现在不再实例化 `KeeperAgent`：

```python
_agent: KeeperSupervisor | None = None

def get_agent() -> KeeperSupervisor:
    global _agent
    if _agent is None:
        _agent = KeeperSupervisor()
    return _agent
```

`KeeperAgent` 仍然保留在 `backend/app/services/agent.py`，但它只是旧代码的兼容壳：

```python
class KeeperAgent(KeeperSupervisor):
    """向后兼容壳：内部逻辑已迁移到 KeeperSupervisor 与各子 Agent。"""
    pass
```

所以要这样理解：

```text
当前主链路：api.py → KeeperSupervisor.run_turn()
旧名称兼容：KeeperAgent 继承 KeeperSupervisor，但当前 API 不直接使用它
旧版参考：_OldKeeperAgent 仍保留在 agent.py 中，用来查看历史 LangGraph 实现
```

如果旧代码里还写 `KeeperAgent().run_turn(...)`，执行效果仍等价于 `KeeperSupervisor().run_turn(...)`，因为 `KeeperAgent` 没有新增逻辑，实际调用的是继承来的 `KeeperSupervisor.run_turn`。

助手接口调用的是另一个独立 Agent：

```text
result = get_assistant_agent().chat(db, message=..., session_id=..., mode=...)
```

所以你可以这样理解：

```text
api.py 负责接收 HTTP 请求。
supervisor.py 负责调度 Agent 处理玩家行动。
assistant_agent.py 负责回答规则和会话问题。
```

### 6.4 为什么有 get_agent 单例

`KeeperSupervisor` 初始化时会创建：

- LLM 客户端。
- Chroma 检索服务。
- 5 个专业 Agent 实例。

这些对象没有必要每个请求都重新创建。

所以项目使用 `_agent` 变量缓存一个实例：

```text
第一次请求：创建 KeeperSupervisor
后续请求：复用同一个 KeeperSupervisor
```

这就是一个简单的进程内单例。

## 7. Agent 初学者重点：多 Agent 架构如何工作

### 7.1 从 LangGraph 到多 Agent

项目早期使用 LangGraph 的 `StateGraph` 编排守秘人回合，所有逻辑在 `_OldKeeperAgent` 的一个类中，通过 12 个节点函数和共享 `KeeperState` 字典串联。

当前版本已迁移到**多 Agent 架构**：

```text
旧版：一个 LangGraph 大类 + 12 个节点函数 + 共享 KeeperState 字典
新版：5 个专业 Agent + 1 个 Supervisor 调度器 + AgentMessage 信封传递
```

旧版代码仍保留在 `agent.py` 的 `_OldKeeperAgent` 中供参考，但不再使用。

### 7.2 多 Agent 架构的核心组件

文件：`backend/app/services/agents/base.py`

| 组件 | 作用 |
|---|---|
| `AgentMessage` | Agent 间传递的消息信封，包含来源、目标、阶段、负载、上下文摘要和元数据 |
| `AgentContext` | 共享只读服务上下文，包含 LLMClient 和 RetrievalService |
| `BaseAgent` | Agent 抽象基类，子类实现 `run(msg) -> AgentMessage` 方法 |

**AgentMessage 信封的关键字段：**

| 字段 | 作用 |
|---|---|
| `from_agent` | 发送方 Agent 名称 |
| `to_agent` | 接收方 Agent 名称 |
| `phase` | 当前阶段（context/plan/execute/narrate/guard） |
| `payload` | 主要数据负载（字典） |
| `context_summary` | 上下文摘要，供下游 Agent 快速了解上游结果 |
| `metadata` | 附加元数据（调试信息等） |

### 7.3 KeeperSupervisor 是什么

文件：`backend/app/services/agents/supervisor.py`

`KeeperSupervisor` 是多 Agent 架构的核心调度器。它不自己做业务逻辑，而是：

1. 按顺序调用各 Agent。
2. 把上一个 Agent 的输出组装成下一个 Agent 的输入。
3. 处理修复循环（GuardAgent 判定需要修复时）。
4. 最终落库。

你可以把它理解为：

```text
KeeperSupervisor = 流程编排器 + 数据搬运工 + 修复循环控制器
```

### 7.4 run_turn 的 5 个 Agent Phase + 修复与落库

文件：`backend/app/services/agents/supervisor.py`

`KeeperSupervisor.run_turn` 先按顺序调度 5 个专业 Agent，然后根据 GuardAgent 的结果决定是否修复，最后统一落库：

```text
Phase 1: 上下文加载
  ContextAgent.run()
  → 加载会话状态、解析意图、RAG 检索

Phase 2: 计划生成
  PlannerAgent.run()
  → LLM 生成回合计划、校验 Tool/Skill 白名单

Phase 3: 计划执行
  ExecutorAgent.run()
  → 执行 Skill、规则检定、综合裁定

Phase 4: 叙事生成
  NarratorAgent.run()
  → 生成守秘人叙事、状态增量、引导选项

Phase 5: 校验与 Reflection
  GuardAgent.run()
  → 确定性校验、Reflection 自检、防剧透清洗

Phase 5.5: 修复循环（如果需要）
  如果 GuardAgent 判定需要修复：
    最多 2 次修复循环
    repair_text → NarratorAgent.repair() → GuardAgent.run()
    repair_state_delta → 修正状态增量后重新 Guard
    ask_clarification / fail_safe → 构造安全追问或兜底响应
    replan_once → 重新规划一次

Phase 6: 落库
  _commit_state()
  → 更新 PostgreSQL + Chroma
```

### 7.5 追问机制

当玩家输入模糊时（如"我看看"），PlannerAgent 会标记 `needs_clarification=True`。

此时 Supervisor 会走 `_clarify_and_commit` 分支：

```text
本轮：
  ContextAgent 先解析玩家原始输入
  → PlannerAgent 标记 needs_clarification=True
  → Supervisor 跳过 Executor/Narrator/Guard
  → _clarify_and_commit 生成追问并落库

下一轮：
  玩家回答追问
  → ContextAgent 读取上一条 TurnLog
  → 将本轮输入视为对追问的回答来解析完整意图
  → 如果意图清晰，再进入正常流程
```

## 8. 5 个专业 Agent 详解

### 8.1 ContextAgent：上下文加载 Agent

文件：`backend/app/services/agents/context_agent.py`

职责：作为回合第一个 Agent，负责"把所有需要的信息准备好"。

核心流程：

```text
1. 从数据库加载会话状态（GameSession、Character、Clue、InventoryItem、TurnLog）
2. 解析玩家意图：
   - 启发式解析（heuristic_intent）：基于关键词的快速回退
   - LLM 解析（build_intent_prompt + chat_json）：更精确的意图理解
   - 合并两者结果，保障鲁棒性
3. 构建上下文：
   - 可见上下文（visible_context）：玩家可见的地点、场景、线索、物品
   - 守秘人专用上下文（keeper_only_context）：剧本秘密、未发现线索
4. RAG 检索：
   - scenario_chunks：剧本片段
   - scenario_entities：实体索引
   - clue_index：线索索引
   - session_memory_chunks：会话记忆
   - rule_chunks：规则片段
```

输出 AgentMessage 包含：意图、可见上下文、守秘人上下文、检索结果。

### 8.2 PlannerAgent：计划生成 Agent

文件：`backend/app/services/agents/planner_agent.py`

职责：基于上下文和意图，生成回合执行计划。

核心流程：

```text
1. 调用 LLM 生成回合计划（turn_plan）
   - 计划包含：allowed_skills、allowed_tools、risk_level 等
2. 规范化计划格式
3. 校验 Tool/Skill 白名单
   - 只允许使用注册过的 Tool 和 Skill
   - 非法工具会被移除
4. 补充默认 Skill（如果计划为空）
5. 处理风险等级
6. 判断是否需要追问（needs_clarification）
```

7 种 Skill 运行时名称：InvestigateSkill、MoveSkill、SocialInteractionSkill、UseItemSkill、DangerAndSanitySkill、CombatLiteSkill、WaitOrObserveSkill。

对应的文件夹名称是：investigate、move、social_interaction、use_item、danger_and_sanity、combat_lite、wait_or_observe。

6 种 Tool：ContextSearchTool、RuleCheckTool、InventoryLookupTool、SceneAffordanceTool、ClueEligibilityTool、MemoryRecallTool

### 8.3 ExecutorAgent：执行 Agent

文件：`backend/app/services/agents/executor_agent.py`

职责：执行 PlannerAgent 生成的计划，进行规则裁定和检定。

核心流程：

```text
1. 执行 Skill（run_generic_skill）
   - 按 allowed_tools 顺序调用各 Tool
   - 收集 Tool 观察结果（tool_observations）
   - 发射调试事件
2. 规则裁定（adjudicate）
   - 判断是否需要技能检定
   - 判断是否需要理智检定
3. 规则检定（roll_tools）
   - 技能检定：D100 对比技能值
   - 理智检定：SAN 检定 + 损失掷骰
   - 重要：骰点结果由代码生成，不让 LLM 编造
4. 综合裁定（build_decision_summary）
   - 汇总 Skill 结果、检定结果、裁定依据
```

### 8.4 NarratorAgent：叙事生成 Agent

文件：`backend/app/services/agents/narrator_agent.py`

职责：调用 LLM 生成守秘人叙事、状态增量和下一步选项。

核心流程：

```text
1. 格式化上下文（各种 _format_* 方法）
   - 将检索结果、检定结果、会话状态格式化为 LLM 可理解的文本
2. 调用 LLM 生成叙事（chat_json）
   - 输出包含：narration、state_delta、options
3. 构建状态增量（_build_state_delta）
   - 地点变化、场景变化、时间推进、线索发现等
4. 追加引导选项
   - 根据剧情偏离或线索可用性，追加引导性选项
5. repair 方法
   - 当 GuardAgent 判定需要修复时，Supervisor 调用此方法重新生成叙事
   - 修复时会附加 GuardAgent 的反馈作为约束
```

### 8.5 GuardAgent：守卫 Agent

文件：`backend/app/services/agents/guard_agent.py`

职责：作为回合最后一个 Agent，确保输出安全、一致、不剧透。

核心流程：

```text
1. 确定性校验（validate_state_delta）
   - 状态增量校验：地点是否合法、数值是否在合理范围
   - 必要字段完整性检查
2. Reflection 自检（_run_reflection）
   - 调用 LLM 对叙事进行自我审查
   - 检查是否剧透、是否矛盾、是否合理
3. 防剧透清洗（sanitize_player_output / sanitize_options）
   - 移除玩家不应知道的内容
   - 替换剧透关键词为模糊表述
4. 修复判断
   - 如果确定性校验或 Reflection 发现问题，标记 needs_repair=True
   - Supervisor 会据此进入修复循环
```

### 9.2 Skill：复合行动模板

| `WaitOrObserveSkill` | `wait_or_observe/` | 等待或观察 |

每个 Skill 子文件夹包含：
- `prompt.py`：Skill 专用的 LLM 提示词
- `skill.py`：Skill 的执行逻辑（定义 allowed_tools 和执行流程）

### 9.3 Skill 执行流程

文件：`backend/app/services/skills/common.py`

`run_generic_skill` 是 Skill 执行的核心函数：

```text
1. 按 allowed_tools 列表顺序调用各 Tool
2. 每个 Tool 调用前后发射调试事件
3. 收集所有 Tool 的观察结果（tool_observations）
4. 如果计划中包含 RuleCheckTool，执行规则检定
5. 汇总结果，构建 skill_results
```

### 9.4 Skill 注册表

文件：`backend/app/services/skills/registry.py`

`SkillRegistry` 管理所有 Skill 的注册和查询：

```text
- 注册时：Skill 名称 → SkillSpec（包含 allowed_tools、描述等）
- 查询时：根据名称获取 SkillSpec
- 白名单校验：PlannerAgent 生成的计划中的 Skill/Tool 必须在注册表中
```

## 10. 剧情状态 story_state 是什么

文件：`backend/app/services/story_state.py`

### 10.1 为什么需要 story_state

数据库中的 `GameSession` 已经有：

- `current_location`
- `current_scene`
- `current_time`
- `danger_level`

但跑团状态远不止这些。

还需要保存：

- 已访问地点。
- 当前可前往地点。
- 已发现线索。
- 未解析线索。
- 已调查对象。
- 当前危险。
- 玩家最近行动。
- 剧情 flag。
- 仪式进度。
- 时间压力。
- 敌对势力警觉。

这些都放在 `session.state` 这个 JSONB 字段中。

`story_state.py` 就是专门维护这个结构的。

### 10.2 三个核心函数

| 函数 | 作用 |
|---|---|
| `ensure_story_state` | 保证状态结构完整 |
| `build_turn_delta` | 构造本回合变化 |
| `apply_turn_delta` | 把本回合变化合并进长期状态 |

### 10.3 ensure_story_state

作用：

```text
不管旧状态缺什么字段，都补成统一结构。
```

为什么需要？

因为：

- 旧存档可能没有新字段。
- 新会话一开始是空状态。
- LLM 状态变更可能缺字段。

有了它，后面代码就可以放心访问：

```text
state["剧情"]
state["场景"]
state["记忆"]
state["秘密"]
```

### 10.4 build_turn_delta

作用：

```text
根据本回合输入、意图、裁定、检定和 LLM 输出，整理出标准变化。
```

它不会直接写数据库。

你可以把它理解成：

```text
本回合变化草稿整理器
```

### 10.5 apply_turn_delta

作用：

```text
把 state_delta 应用到 story_state 上。
```

它会更新：

- 当前地点。
- 当前场景。
- 当前时间。
- 危险等级。
- 已访问地点。
- 可前往地点。
- 已调查对象。
- 最近行动。
- 重要裁定记录。

最终结果会保存在 `session.state`。

## 11. RAG 是如何工作的

### 11.1 RAG 的一句话解释

RAG 是 Retrieval-Augmented Generation，中文常译为“检索增强生成”。

简单说：

```text
先从资料库找相关内容，再让 LLM 基于这些内容回答。
```

### 11.2 本项目为什么需要 RAG

因为守秘人要参考：

- 《无光的灯塔》剧本。
- 守秘人规则书。
- 调查员手册。
- 结构化地点/NPC/物品。
- 当前会话已经发生过的事情。

这些内容不应该全部塞进每次 prompt。

原因：

- 文本太长。
- 成本高。
- LLM 容易抓不住重点。
- 可能增加剧透风险。

所以项目先把资料切块、向量化、存进 Chroma。每次玩家行动时，只检索最相关的一小部分。

### 11.3 Chroma 集合

文件：`backend/app/services/retrieval.py`

本项目常用集合：

| 集合名 | 内容 | 何时使用 |
|---|---|---|
| `scenario_chunks` | 剧本文本分块 | 生成叙事、判断场景事实 |
| `rule_chunks` | 规则书分块 | 行动裁定、规则说明 |
| `scenario_entities` | 地点、NPC、物品等结构化实体 | 推断当前位置和可前往地点 |
| `clue_index` | 线索索引 | 判断是否发现新线索 |
| `session_memory_chunks` | 当前会话长期记忆 | 让后续回合记得玩家经历 |

### 11.4 Embedding 是什么

Embedding 是把文本变成数字向量。

例如：

```text
"灯塔门口的脚印" -> [0.12, -0.03, 0.77, ...]
```

相似意思的文本，向量距离会更近。

所以当玩家输入：

```text
我检查码头有没有痕迹
```

系统可以找到与“码头”“痕迹”“脚印”“登陆点”等相关的剧本片段。

### 11.5 两个数据库的工作逻辑：PostgreSQL 与 Chroma

本项目同时使用两个数据库：

- **PostgreSQL**：关系型数据库，负责保存“游戏事实”和“业务状态”。
- **Chroma**：向量数据库，负责保存“可被语义检索的文本资料”和“会话记忆”。

最重要的一句话是：

```text
PostgreSQL 回答：现在这局游戏真实发生了什么？
Chroma 回答：哪些文本资料和当前玩家行动语义最相关？
```

也可以这样理解：

```text
PostgreSQL = 存档系统
Chroma = 资料检索系统
```

#### 11.5.1 为什么不能只用一个数据库

如果只用 PostgreSQL：

- 可以稳定保存角色、会话、线索、物品。
- 但它不擅长回答“哪几段剧本文本和玩家这句话最相似”。
- 用普通 SQL `LIKE` 搜索很难理解同义词和语义接近的表达。

如果只用 Chroma：

- 可以按语义找相似文本。
- 但它不适合维护复杂业务关系，例如会话属于哪个角色、线索是否重复、物品数量是多少。
- 它也不适合作为页面右侧状态栏的权威存档来源。

所以本项目把职责拆开：

| 数据库 | 主要职责 | 典型问题 |
|---|---|---|
| PostgreSQL | 精确保存结构化游戏状态 | 当前角色是谁？当前位置是哪？已发现哪些线索？物品栏有什么？ |
| Chroma | 按语义检索相关文本 | 玩家说“检查痕迹”时，哪些剧本片段、规则片段、历史记忆最相关？ |

#### 11.5.2 两个数据库分别存什么

PostgreSQL 保存的是结构化数据。

对应文件：

- `backend/app/models.py`
- `backend/app/database.py`
- `backend/app/api.py`
- `backend/app/services/agents/context_agent.py`
- `backend/app/services/agents/supervisor.py`

主要表：

| 表 | 保存内容 | 是否直接影响前端显示 |
|---|---|---|
| `scenarios` | 剧本基本信息 | 间接影响 |
| `characters` | 预设调查员 | 是 |
| `sessions` | 当前会话、地点、场景、时间、剧情状态 JSON | 是 |
| `turn_logs` | 每回合输入、检索、骰点、叙事、状态变化 | 调试时影响 |
| `clues` | 玩家已发现线索 | 是 |
| `inventory_items` | 当前物品栏 | 是 |
| `story_flags` | 剧情标记 | 是 |

Chroma 保存的是文本向量。

对应文件：

- `backend/app/services/retrieval.py`
- `backend/app/services/importer.py`
- `backend/app/services/chunking.py`
- `backend/app/services/content_index.py`
- `backend/app/services/llm.py`
- `backend/app/services/agents/context_agent.py`

主要集合：

| 集合 | 保存内容 | 什么时候用 |
|---|---|---|
| `scenario_chunks` | 剧本文本切块后的向量 | 生成守秘人叙事时检索剧本事实 |
| `rule_chunks` | 规则书文本切块后的向量 | 需要规则裁定时检索规则资料 |
| `scenario_entities` | 地点、NPC、物品等实体索引 | 判断当前位置、可见地点、相关实体 |
| `clue_index` | 线索索引 | 判断玩家行动是否可能发现线索 |
| `session_memory_chunks` | 当前会话每回合摘要和长期记忆 | 后续回合回忆玩家过去做过什么 |

#### 11.5.3 初始化和导入阶段：两个数据库分别做什么

初始化接口：

```text
POST /coc/api/init
```

这一步主要影响 PostgreSQL。

流程是：

```text
api.py
  -> initialize_database
  -> init_db
  -> Base.metadata.create_all
  -> PostgreSQL 中创建表
```

它只是建表，不负责把剧本和规则书放进 Chroma。

导入接口：

```text
POST /coc/api/import
```

这一步会同时影响 PostgreSQL 和 Chroma。

流程可以拆成两条线：

```text
导入剧本基本信息和角色
  -> 写入 PostgreSQL

切分剧本、规则书、实体、线索索引
  -> 生成 Embedding
  -> 写入 Chroma
```

更具体地说：

1. `import_default_content` 会先检查 PostgreSQL 中是否已有《无光的灯塔》这个 `Scenario`。
2. 如果没有，就在 PostgreSQL 的 `scenarios` 表中创建一条剧本记录。
3. 如果启用角色导入，就把预设人物卡导入 PostgreSQL 的 `characters` 表。
4. 后端读取剧本文档，把 Markdown 切成多个 `scenario_chunks`。
5. 后端提取结构化地点、NPC、物品等，写入 `scenario_entities`。
6. 后端提取线索索引，写入 `clue_index`。
7. 后端读取规则书，切成多个 `rule_chunks`。
8. 这些文本块会通过 Embedding 模型转成向量，再 upsert 到 Chroma。

所以导入完成后：

```text
PostgreSQL 中有：剧本记录、角色记录。
Chroma 中有：剧本文本向量、规则文本向量、实体向量、线索索引向量。
```

#### 11.5.4 PostgreSQL 为什么也要保存剧本相关信息

看到这里你可能会有一个疑问：

```text
既然剧本文本已经切块后放进 Chroma，
为什么 PostgreSQL 里还需要 scenarios 这张表？
```

原因是：PostgreSQL 保存的不是“用于语义检索的完整剧本文本”，而是“业务系统需要精确引用的剧本身份信息”。

可以这样区分：

| 内容 | 更适合放在哪里 | 原因 |
|---|---|---|
| 剧本名称，例如《无光的灯塔》 | PostgreSQL | 需要精确查询、关联角色和会话 |
| 剧本文件路径 | PostgreSQL | 导入、管理和排查时需要知道来源 |
| 剧本时代、地点等元数据 | PostgreSQL | 页面展示、会话创建、筛选时需要结构化字段 |
| 剧本文本正文 | Chroma | 太长，更适合切块后做语义检索 |
| 剧本地点/NPC/线索片段 | Chroma | 玩家行动时需要按语义召回相关片段 |

也就是说：

```text
PostgreSQL 中的 Scenario 是“剧本档案卡”。
Chroma 中的 scenario_chunks 是“剧本正文资料库”。
```

这个设计有几个实际好处。

第一个好处是：会话和角色需要有稳定归属。

`GameSession` 里有 `scenario_id`，`Character` 里也有 `scenario_id`。  
这表示：

```text
这个会话属于哪个剧本？
这个角色属于哪个剧本？
```

如果将来项目支持多个剧本，例如：

```text
无光的灯塔
鬼屋
边缘之地
```

那么 PostgreSQL 可以很清楚地保存：

```text
会话 A 属于《无光的灯塔》
会话 B 属于《鬼屋》
角色 X 属于《无光的灯塔》
角色 Y 属于《边缘之地》
```

第二个好处是：业务查询需要精确匹配。

例如导入时，代码会先检查：

```text
PostgreSQL 里是否已经存在名为“无光的灯塔”的 Scenario？
```

如果存在，就复用它。  
如果不存在，就创建一条新的 `Scenario` 记录。

这种“是否已经存在某个剧本”的判断，适合用 PostgreSQL 做，因为它需要精确匹配，而不是语义相似。

第三个好处是：Chroma 负责检索，不适合作为权威业务索引。

Chroma 擅长回答：

```text
哪些文本和“灯塔门口的脚印”最相似？
```

但它不适合作为唯一来源回答：

```text
当前系统有几个剧本？
某个角色属于哪个剧本？
某个会话应该加载哪个剧本？
删除某个剧本时要影响哪些会话？
```

这些问题需要稳定的主键、外键和关系约束，所以更适合 PostgreSQL。

第四个好处是：前端和 API 需要稳定 ID。

前端创建会话时，后端最终需要知道：

```text
创建的是哪个剧本下的会话？
使用的是哪个剧本下的角色？
```

这类数据不能依赖“向量相似度搜索”得到，而应该依赖明确的数据库 ID。

因此，两个数据库对剧本的分工是：

```text
PostgreSQL：
  保存剧本是谁、来自哪里、和哪些角色/会话有关。

Chroma：
  保存剧本内容是什么，并支持按玩家输入检索相关片段。
```

如果导入时选择 `reset_chroma=true`：

```text
只会清空并重建 Chroma 中的向量集合。
不会等同于清空 PostgreSQL 的所有业务表。
```

#### 11.5.5 创建会话阶段：主要写 PostgreSQL

创建会话接口：

```text
POST /coc/api/sessions
```

这一步主要写 PostgreSQL。

创建新会话时，后端会：

1. 选择一个角色。
2. 创建 `GameSession`。
3. 初始化当前位置、当前场景、当前时间、危险等级。
4. 初始化 `session.state` 中的剧情状态。
5. 同步角色初始物品到 `inventory_items`。

这时通常不会立刻向 Chroma 写入新的会话记忆。

原因是：

```text
新会话刚创建，还没有玩家行动，也就没有可总结的回合记忆。
```

#### 11.5.6 每次玩家行动前：先读 PostgreSQL，再查 Chroma

玩家提交行动后，后端进入 `KeeperSupervisor.run_turn`。

第一步由 ContextAgent 执行，它承担了旧版 `load_state`、可见上下文构建和检索相关节点的职责。

它读取 PostgreSQL：

```text
GameSession
Character
Clue
InventoryItem
StoryFlag
TurnLog
```

这一步的目的不是检索资料，而是确认“当前游戏真实状态”：

- 玩家当前在哪里？
- 当前是什么场景？
- 当前时间是多少？
- 角色当前 HP、SAN、物品是什么？
- 玩家已经发现了哪些线索？
- 最近几回合发生了什么？

接着 ContextAgent 继续执行 RAG 检索。

它查询 Chroma：

```text
scenario_chunks
scenario_entities
clue_index
session_memory_chunks
rule_chunks
```

这一步的目的不是读取存档，而是找到“和本回合最相关的文本”。

查询文本通常会结合：

- 玩家本回合输入。
- 当前地点。
- 当前场景。
- 解析出的行动目标。
- 推断出的技能。

例如玩家输入：

```text
我检查码头附近有没有脚印。
```

PostgreSQL 会告诉 Agent：

```text
当前地点：北岸码头
当前角色：调查局探员
已发现线索：旧船票、湿透的地图
物品栏：手电筒、左轮手枪
```

Chroma 会返回类似：

```text
和“码头”“脚印”“痕迹”“北岸”语义接近的剧本片段
和“侦查检定”相关的规则片段
和当前会话过去调查码头相关的记忆
```

两边结果合在一起，才会成为 LLM 的上下文。

#### 11.5.7 每次玩家行动后：PostgreSQL 记录事实，Chroma 记录记忆

一次多 Agent 回合快结束时，Supervisor 会调用 `_commit_state`。

这一步会同时写 PostgreSQL 和 Chroma，但写入内容不同。

PostgreSQL 写入的是权威事实：

| 写入内容 | 保存位置 |
|---|---|
| 当前地点、场景、时间、危险等级 | `sessions` |
| 结构化剧情状态 | `sessions.state` |
| 新发现线索 | `clues` |
| 物品变化 | `inventory_items` |
| 回合输入、意图、检索、骰点、回应、状态变化 | `turn_logs` |
| 剧情摘要 | `sessions.summary` |

Chroma 写入的是可检索记忆：

| 写入内容 | 保存位置 |
|---|---|
| 本回合玩家做了什么、守秘人如何回应、发生了什么结果 | `session_memory_chunks` |
| 当前会话摘要记忆 | `session_memory_chunks` |

为什么回合日志要放 PostgreSQL，而会话记忆还要放 Chroma？

因为二者用途不同：

```text
TurnLog 用来精确查看某一回合完整记录。
session_memory_chunks 用来让未来回合按语义找回相关经历。
```

例如第 3 回合玩家在码头发现了脚印。第 18 回合玩家又提到“之前岸边的痕迹”。  
如果只看最近几条 `TurnLog`，第 3 回合可能已经太远了。  
但 Chroma 可以通过“岸边”“痕迹”和“脚印”的语义相似性，把旧记忆重新找出来。

#### 11.5.8 删除会话时：两个数据库都要清理

删除会话接口：

```text
DELETE /coc/api/sessions/{session_id}
```

它会做两类清理：

1. 删除 PostgreSQL 中的 `GameSession`。
2. 同步删除 Chroma 中 `session_memory_chunks` 里对应 `session_id` 的会话记忆。

为什么要清理 Chroma？

因为如果只删 PostgreSQL，不删 Chroma，会出现这种问题：

```text
数据库里这局游戏已经不存在了。
但向量库里还残留这局游戏的记忆。
未来检索时可能把旧存档内容找出来。
```

这会污染新会话的上下文。

#### 11.5.9 前端主要相信谁

前端页面展示主要相信 PostgreSQL 返回的数据。

例如：

- 当前地点。
- 当前场景。
- 当前时间。
- 角色状态。
- 线索簿。
- 物品栏。
- 剧情状态。
- 回合历史。

这些都来自后端 API 返回的 `session`，而 `session` 本质上来自 PostgreSQL。

Chroma 的结果通常不会直接作为页面状态显示。

它主要作为 LLM 的参考资料：

```text
玩家不可直接看到 Chroma 原始检索结果。
LLM 会基于检索结果生成 narration。
后端再把 narration 和状态变化返回前端。
```

调试面板或 `TurnLog.retrieval` 可能会保存部分检索结果摘要，方便开发者排查问题。

#### 11.5.10 一次玩家行动中的两个数据库顺序图

```text
玩家输入行动
  ↓
FastAPI 接收请求
  ↓
KeeperSupervisor.run_turn
  ↓
ContextAgent
  ↓
读取 PostgreSQL：会话、角色、线索、物品、历史回合
  ↓
解析意图 + RAG 检索
  ↓
查询 Chroma：剧本、规则、实体、线索索引、会话记忆
  ↓
PlannerAgent → ExecutorAgent → NarratorAgent → GuardAgent
  ↓
（修复循环，如果需要）
  ↓
_commit_state
  ↓
写 PostgreSQL：状态、线索、物品、回合日志、摘要
  ↓
写 Chroma：本回合长期记忆和摘要记忆
  ↓
返回前端
```

#### 11.5.11 调试时如何判断问题出在哪个数据库

如果页面上的状态不对，优先查 PostgreSQL 相关逻辑。

例如：

- 角色没加载。
- 会话列表为空。
- 线索簿没显示。
- 物品栏没更新。
- 当前地点没有变化。
- 回合日志缺失。

优先看：

- `backend/app/models.py`
- `backend/app/api.py`
- `backend/app/services/agents/context_agent.py`（加载会话状态）
- `backend/app/services/agents/supervisor.py` 的 `_commit_state`
- `backend/app/services/story_state.py`

如果守秘人“不知道剧本内容”或“经常答非所问”，优先查 Chroma/RAG 相关逻辑。

例如：

- 明明剧本里有码头信息，守秘人却说不知道。
- 规则裁定缺少依据。
- 很久以前发生过的事，后续回合完全想不起来。
- 检索结果和玩家输入无关。

优先看：

- `backend/app/services/importer.py`
- `backend/app/services/chunking.py`
- `backend/app/services/content_index.py`
- `backend/app/services/retrieval.py`
- `backend/app/services/llm.py`
- `TurnLog.retrieval`

#### 11.5.12 最小总结

```text
PostgreSQL 是权威存档：
保存“已经发生、已经确认、需要精确展示”的游戏事实。

Chroma 是语义资料库：
保存“可以被相似度搜索召回”的剧本、规则、线索索引和会话记忆。

一次回合通常是：
先从 PostgreSQL 读当前事实，
再从 Chroma 找相关资料，
生成结果后把事实写回 PostgreSQL，
再把本回合摘要写进 Chroma，供未来检索。
```

## 12. 数据库模型如何理解

文件：`backend/app/models.py`

### 12.1 核心表

| 模型 | 表名 | 作用 |
|---|---|---|
| `Scenario` | `scenarios` | 剧本，例如《无光的灯塔》 |
| `Character` | `characters` | 预设调查员角色 |
| `GameSession` | `sessions` | 玩家一次游戏存档 |
| `TurnLog` | `turn_logs` | 每一回合的输入、检索、骰点、回应和状态变化 |
| `Clue` | `clues` | 玩家已发现线索 |
| `InventoryItem` | `inventory_items` | 当前会话物品栏 |
| `StoryFlag` | `story_flags` | 结构化剧情标记 |
| `AgentTraceRun` | `agent_trace_runs` | 一次行动或助手请求的监控运行记录 |
| `AgentTraceRecord` | `agent_trace_records` | Agent/Skill/Tool/LLM 步骤输入输出记录 |
| `AgentTraceSettings` | `agent_trace_settings` | Agent 监控记录保留上限等配置 |

### 12.2 最重要的是 GameSession

`GameSession` 表示一局游戏。

它保存：

- 当前角色。
- 当前地点。
- 当前场景。
- 当前时间。
- 危险等级。
- 剧情摘要。
- 结构化状态 `state`。

前端右侧状态栏大部分内容都来自当前 `session`。

### 12.3 TurnLog 是调试神器

每次玩家行动后，都会写入一条 `TurnLog`。

它包含：

- 玩家输入。
- 解析出的意图。
- 检索和调试摘要。
- 裁定结果。
- 骰点结果。
- 守秘人回应。
- 状态变化。
- 配图 URL 和配图元数据。

如果你想调试“为什么守秘人这么回答”，应该优先看 `turn_logs`。

### 12.4 AgentTraceRun / AgentTraceRecord 是更细的监控日志

`TurnLog` 更偏“回合结果”，而 `AgentTraceRecord` 更偏“执行过程”。

当前 `api.py` 会在主回合请求和助手请求开始时创建 `AgentTraceRun`，然后把 ContextAgent、PlannerAgent、Skill、Tool、LLM 生成等步骤记录为多条 `AgentTraceRecord`。

可以这样区分：

| 记录 | 粒度 | 适合排查什么 |
|---|---|---|
| `TurnLog` | 一回合一条 | 最终叙事、骰点、状态变化、线索是否写入 |
| `AgentTraceRecord` | 一个步骤一条 | 哪个 Agent 输入了什么、输出了什么、哪一步失败或耗时异常 |

前端的 `monitor.tsx` 页面会读取 `/coc/api/monitor/...` 系列接口，用来查看和清理这些监控记录。

## 13. 游戏助手 Agent：独立于主回合的辅助系统

文件：`backend/app/services/assistant_agent.py`

### 13.1 GameAssistantAgent 是什么

`GameAssistantAgent` 是一个独立于主回合流程的辅助 Agent，专门回答玩家关于规则和当前会话状态的问题。

关键特点：

```text
不参与主回合流程 → 不调用 run_turn
不修改游戏状态 → 不写 GameSession/TurnLog/线索/物品
独立检索和回答 → 有自己的检索策略
```

注意：为了调试，助手请求仍会写入 `AgentTraceRun` 和 `AgentTraceRecord` 监控记录。这不属于游戏状态变更。

### 13.2 核心检索策略

| 策略 | 全称 | 作用 |
|---|---|---|
| MQE | Multi-Query Expansion | 把用户问题扩展为多个查询，提高召回率 |
| HyDE | Hypothetical Document Embedding | 让 LLM 生成假设性回答，用回答的向量去检索 |

MQE 流程：

```text
用户问题："侦查技能怎么用？"
  ↓
LLM 生成多个查询变体：
  - "侦查检定的规则"
  - "Spot Hidden 如何判定"
  - "观察类技能检定方法"
  ↓
分别检索，合并去重排序
```

HyDE 流程：

```text
用户问题："SAN 值怎么恢复？"
  ↓
LLM 生成假设性回答（可能不完全正确）
  ↓
用假设性回答的 Embedding 去检索
  ↓
找到真正相关的规则片段
```

### 13.3 检索范围

助手当前按模式选择检索集合：

| 模式 | 检索集合 | 说明 |
|---|---|---|
| `rules` | `rule_chunks` | 只查规则书片段 |
| `session_help` | `session_memory_chunks` + `rule_chunks` | 绑定会话时查当前会话记忆和规则书 |
| `auto` | 自动推断为上面两种之一 | 根据问题中是否出现“我现在、线索、去哪、下一步”等词判断 |

检索后会过滤 `visibility=keeper_only` 或 `secret_level=主持人秘密` 的内容，也会过滤玩家尚未发现的线索。

### 13.4 防剧透清洗

助手回答也会经过防剧透清洗，确保不会泄露剧本秘密。

### 13.5 引用构建

助手回答会附带引用（citation），标注信息来源：

```text
来源类型：rulebook / investigator_handbook / memory / unknown 等
来源片段：原文摘要
引用片段：最多取前 240 个字符
```

### 13.6 前端交互

前端右下角有"游戏助手"抽屉，开关状态保存在 `localStorage` 的 `coc-lite-game-assistant-open` 键中。

助手支持三种模式：

| 模式 | 说明 |
|---|---|
| `auto` | 自动判断使用规则查询还是当前局势查询 |
| `rules` | 规则查询模式，专注规则书检索 |
| `session_help` | 当前局势模式，检索当前会话记忆和规则书 |

## 14. 调试与监控系统

文件：`backend/app/services/debug_events.py`

### 14.1 为什么需要调试事件

主回合流程涉及 5 个 Agent、多个 Tool 和 Skill 调用，执行时间可能较长。

如果没有实时调试，开发者只能等回合结束后看 `TurnLog`，无法了解中间过程。

`DebugEmitter` 通过 NDJSON 流实时推送调试事件，让前端在回合执行过程中就能看到进度。

### 14.2 DebugEmitter 的工作原理

```text
1. `submit_action_stream` 内部创建一个 `Queue`
2. `debug_emit` 回调把事件放入 Queue
3. 各 Agent/Tool/Skill 在关键节点调用 `emit_debug(...)`
4. 流式接口从 Queue 取出事件
5. 作为 NDJSON 行推送给前端
6. 前端 DebugConsolePanel 实时显示
```

### 14.3 调试事件类型

| `phase` | 常见 `name` | 内容 |
|---|---|---|
| `stream` | `action_stream` / `supervisor` | 流式请求和 Supervisor 总体进度 |
| `agent_node` | `ContextAgent` / `PlannerAgent` / `ExecutorAgent` / `NarratorAgent` / `GuardAgent` | 专业 Agent 开始、完成或失败 |
| `agent_step` | `retrieve_context` / `parse_intent` / `reflection_review` | Agent 内部子步骤 |
| `skill` | `InvestigateSkill` 等 | Skill 执行状态 |
| `tool` | `ContextSearchTool` / `RuleCheckTool` 等 | Tool 调用开始、成功、警告或失败 |
| `assistant` | `expand_queries` / `retrieve` / `generate_answer` | 游戏助手检索和回答生成进度 |

### 14.4 前端调试面板

前端左下角的 `DebugConsolePanel` 最多保留 200 条日志，支持滚动查看。

回合结束后，`TurnLog.retrieval` 会保存回合计划、ReAct 轨迹、Tool 观察、Skill 结果、Reflection 和最终校验摘要，方便回溯。

### 14.5 Agent Monitor 监控页面

除了左下角实时调试控制台，项目还有更细的 Agent Monitor：

| 接口 | 用途 |
|---|---|
| `GET /coc/api/monitor/settings` | 查看监控记录上限和当前数量 |
| `PUT /coc/api/monitor/settings` | 调整监控记录保留上限 |
| `GET /coc/api/monitor/runs` | 查看 action / assistant 运行记录 |
| `GET /coc/api/monitor/records` | 查看单步 Agent/Skill/Tool/LLM 记录 |
| `GET /coc/api/monitor/events/stream` | 实时推送监控事件 |
| `DELETE /coc/api/monitor/...` | 删除运行或步骤记录 |

它和 DebugEmitter 的区别：

```text
DebugEmitter：给玩家界面左下角看实时进度，轻量、短期、最多 200 条。
Agent Monitor：把步骤输入输出写入数据库，适合开发者复盘和定位具体失败点。
```

## 15. 提示词 prompt 如何理解

文件：`backend/app/services/prompt_config.py`

### 15.1 为什么提示词单独放一个文件

这样做有几个好处：

- 业务代码更清晰。
- 调整模型行为时不用改 Agent 流程。
- 可以集中维护输出格式。
- 可以集中维护防剧透要求。

### 15.2 核心提示词

| 提示词 | 作用 | 使用者 |
|---|---|---|
| `INTENT_SYSTEM_PROMPT` | 告诉 LLM 如何解析玩家意图 | ContextAgent |
| `KEEPER_RESPONSE_SYSTEM_PROMPT` | 告诉 LLM 如何生成守秘人回应 | NarratorAgent |
| `TURN_PLAN_SYSTEM_PROMPT` | 告诉 LLM 如何生成回合计划 | PlannerAgent |
| `REFLECTION_SYSTEM_PROMPT` | 告诉 LLM 如何进行 Reflection 自检 | GuardAgent |
| `TURN_SUMMARY_PROMPT` | 告诉 LLM 如何生成回合摘要 | Supervisor（落库时） |

此外，每个 Skill 子文件夹中的 `prompt.py` 也包含 Skill 专用的提示词，每个 Tool 模块内也定义了自身的说明和约束。

### 15.3 意图解析提示词

它要求 LLM 输出 JSON，字段包括：

- `action_type`
- `target`
- `skill`
- `needs_clarification`
- `clarification_question`
- `is_meta`
- `reason`

这样后续 Agent 就不需要解析自然语言，而是处理结构化字段。

### 15.4 守秘人回应提示词

它要求 LLM 输出：

- `narration`
- `options`
- `state_delta`
- `discovered_clues`

并且要求：

- 不要剧透。
- 不要替玩家做重大决定。
- 不要重写骰点结果。
- 不要编造关键事实。
- 描写玩家可以感知到的内容。

### 15.5 回合计划提示词

它要求 LLM 输出回合执行计划，字段包括：

- `skill`：使用哪个 Skill
- `allowed_tools`：需要调用哪些 Tool
- `risk_level`：风险等级
- `reasoning`：计划推理过程

PlannerAgent 会校验计划中的 Skill/Tool 是否在白名单中。

### 15.6 Reflection 提示词

它要求 LLM 对当前叙事进行自我审查，检查：

- 是否剧透
- 是否与已知事实矛盾
- 是否合理
- 是否需要修复

GuardAgent 的 `_run_reflection` 方法使用此提示词。

## 16. 一次玩家行动的完整生命周期

下面用一个具体例子串起来。

玩家输入：

```text
我划向北岸码头，检查附近有没有脚印。
```

### 16.1 前端阶段

文件：`frontend/src/App.tsx`

1. 用户点击发送。
2. `send(message)` 被调用。
3. 前端追加玩家消息。
4. 前端追加空的守秘人消息。
5. 调用 `api.streamAction(session.id, message, onEvent)`。

### 16.2 API 封装阶段

文件：`frontend/src/api.ts`

1. 拼接 URL：`/coc/api/sessions/{id}/actions/stream`。
2. 使用 `fetch` 发送 POST 请求。
3. 请求体是：

```json
{
  "message": "我划向北岸码头，检查附近有没有脚印。"
}
```

4. 开始读取 NDJSON 流。

### 16.3 FastAPI 阶段

文件：`backend/app/api.py`

1. 请求进入 `submit_action_stream`。
2. 检查 `session_id` 是否存在。
3. 创建 `event_stream` 生成器。
4. 先返回 `start` 事件。
5. 调用 `get_agent().run_turn(...)`。

### 16.4 多 Agent 阶段

文件：`backend/app/services/agents/supervisor.py`

Supervisor 开始调度各 Agent：

```text
ContextAgent
  读取当前会话、角色、线索、物品
  解析意图：移动 + 调查，目标是北岸码头/脚印，可能技能是侦查
  RAG 检索：码头、脚印、北岸、剧本片段、规则片段、历史记忆

PlannerAgent
  生成回合计划：allowed_skills=[InvestigateSkill], allowed_tools=[ContextSearchTool, ClueEligibilityTool, RuleCheckTool]
  校验白名单通过
  判断不需要追问

ExecutorAgent
  执行 InvestigateSkill，依次调用各 Tool
  规则裁定：需要侦查检定
  骰点：D100=45，侦查技能=60，检定成功
  综合裁定：发现脚印线索

NarratorAgent
  调用 LLM 生成叙事、选项、状态增量
  构建状态增量：地点→北岸码头，时间推进，线索→码头脚印

GuardAgent
  确定性校验：地点合法、数值合理
  Reflection 自检：无剧透、无矛盾
  防剧透清洗：通过
  判定不需要修复
```

如果 GuardAgent 判定需要修复，Supervisor 会调用 `NarratorAgent.repair()` 重新生成，最多 2 次修复循环。

### 16.5 返回前端阶段

文件：`backend/app/api.py`

`event_stream` 会把叙事分块返回：

```json
{"type":"start"}
{"type":"debug","event":{"phase":"agent_node","name":"ContextAgent","status":"start","message":"ContextAgent 开始加载状态与检索。"}}
{"type":"chunk","content":"你顶着海风划向北岸码头，"}
{"type":"chunk","content":"木桩间传来潮水拍击声。"}
```

最后返回完整结果：

```json
{
  "type": "final",
  "response": {
    "session": {...},
    "narration": "完整叙事",
    "options": ["检查脚印", "观察码头木屋", "自定义行动"],
    "dice_results": [...],
    "skill_checks": [...],
    "sanity_checks": [...],
    "discovered_clues": [...],
    "state_delta": {...},
    "needs_clarification": false,
    "needs_image": false,
    "image_url": null
  }
}
```

如果本回合需要配图，`final` 后还可能收到：

```json
{"type":"image","url":"https://...","turnId":"...","metadata":{...}}
```

### 16.6 页面更新阶段

文件：`frontend/src/App.tsx`

1. `chunk` 到达时，前端调用 `appendToLastKeeperMessage`。
2. `final` 到达时，前端调用 `applyActionResponse`。
3. 页面更新：
   - 聊天区显示完整叙事。
   - 下一步按钮刷新。
   - 右侧状态栏刷新。
   - 线索簿刷新。
   - 物品栏刷新。
   - 调试信息刷新。
   - 如果有 `image` 事件，给当前守秘人消息补上配图。

## 17. 如何调试本项目

1. 看后端终端日志。

6. 看 `adjudication` 和 `dice_results` 是否合理（ExecutorAgent 职责）。

重点文件：

- `backend/app/services/agents/supervisor.py`

### 17.4 实时调试控制台

文件：`backend/app/services/debug_events.py`

后端在回合执行过程中会通过 `DebugEmitter` 发射调试事件，前端通过 NDJSON 流实时展示在左下角调试控制台。

| 事件类型 | 来源 | 内容 |

### 17.5 RAG 调试路线

如果模型不知道剧本内容：

1. 确认是否执行过导入。

## 19. 初学者容易混淆的概念

### 19.1 session 和 state

`session` 是数据库中的一局游戏。

`session.state` 是这局游戏里的结构化 JSON 状态。

可以理解为：

```text
session = 存档盒子
session.state = 存档盒子里的复杂剧情记录
```

### 19.2 AgentMessage 和 story_state

`AgentMessage`：

```text
Agent 间传递的消息信封，生命周期仅在一次回合的 Agent 调用链中。
```

`story_state`：

```text
长期保存到数据库中的剧情状态。
```

区别：

| 项 | 生命周期 | 是否长期保存 |
|---|---|---|
| `AgentMessage` | 一次 Agent 调用 | 否，运行时中间数据 |
| `story_state` | 整个会话 | 是，保存到 `session.state` |

注意：旧版的 `KeeperState`（LangGraph 共享字典）已被 `AgentMessage` 信封替代。`KeeperState` 仍保留在 `agent.py` 中供旧版参考，但不再使用。

### 19.3 narration 和 keeper_response

`narration` 是本回合 Agent 生成的守秘人叙事。

`keeper_response` 是写入 `TurnLog` 后的字段名。

可以理解为：

```text
运行时叫 narration
落库日志里叫 keeper_response
```

### 19.4 options 和玩家输入

`options` 是系统推荐按钮，不限制玩家只能选这些。

玩家仍然可以输入自定义行动。

### 19.5 Chroma 和 PostgreSQL

更完整的工作流程可以回看 `11.5 两个数据库的工作逻辑：PostgreSQL 与 Chroma`。

PostgreSQL 保存结构化游戏数据：

- 会话。
- 角色。
- 线索。
- 物品。
- 回合日志。

Chroma 保存用于语义检索的文本向量：

- 剧本片段。
- 规则片段。
- 会话记忆。

简单说：

```text
PostgreSQL 负责“事实存档”。
Chroma 负责“相似文本检索”。
```

### 20.2 为什么 API Key 不能写进代码

API Key 是访问模型服务的凭证。

如果写进代码：

- 容易提交到 Git。
- 容易泄露给别人。
- 可能产生费用风险。

所以本项目通过 `.env` 配置。

### 20.3 LLM 未配置时会怎样

`backend/app/services/llm.py` 中有兜底逻辑。

如果聊天模型没有配置：

- `chat_text` 返回空字符串。
- `chat_json` 返回 fallback。

也就是说，部分流程仍可运行，但智能叙事能力会明显下降。

如果 Embedding 没配置：

- `EmbeddingClient` 会使用 `fallback_embedding`。
- 这可以保证系统不立刻崩溃。
- 但真实语义检索效果会不如正式 Embedding 模型。

如果图片生成没配置：

- `ImageGenerator.generate_image` 会返回 `None`。
- 主回合仍会正常完成，只是不会返回配图 URL。
- 如果配置了 `DRAWING_LLM_*`，系统会先用这个模型优化配图 prompt；留空则复用主 LLM，主 LLM 也没有时直接使用叙事摘要。

## 23. 常见问题

### 23.1 为什么前端 API 路径不是直接 `/api`

因为项目部署在 `/coc` 子路径下。

最终后端路径是：

```text
/coc/api/...
```

前端使用：

```text
import.meta.env.BASE_URL
```

来自动拼接基础路径。

### 23.2 为什么需要流式接口

如果只用普通接口，玩家要等完整回合执行完才能看到文本。

流式接口可以先显示叙事片段，提高响应体验。

### 23.3 为什么 LLM 要输出 JSON

因为后端需要稳定读取字段。

如果让 LLM 输出自然语言，后端很难可靠判断：

- 叙事是哪部分。
- 选项是哪部分。
- 状态变化是哪部分。
- 线索是哪部分。

JSON 可以让后续代码更稳定。

### 23.4 为什么还要校验 LLM 输出

因为 LLM 可能不稳定。

它可能：

- 输出非法 JSON。
- 编造地点。
- 泄露秘密。
- 给出过大的状态变化。
- 产生格式不一致的字段。

所以本项目使用 fallback、状态校验、防剧透过滤来降低风险。

### 23.5 为什么有 PostgreSQL 又有 Chroma

它们解决的问题不同。

PostgreSQL：

```text
精确保存结构化事实。
```

Chroma：

```text
根据语义相似度查找相关文本。
```

两者互补，不是替代关系。
