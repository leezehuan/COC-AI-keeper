# coc-lite 初学者学习指南

> 面向 **LangGraph 初学者** 和 **Web 初学者** 的项目理解文档。  
> 目标不是只告诉你“代码在哪里”，而是帮助你理解：浏览器里的一个按钮点击，如何一路变成后端的一次 `LangGraph` 守秘人回合，最后又如何回到页面上显示为叙事、选项、线索、物品和状态变化。

---

## 0. 这份文档适合谁

如果你符合下面任意一种情况，这份文档都适合从头看：

- **你会一点前端，但不熟悉后端**：你可以重点看 Web 请求链路、FastAPI、接口返回结构。
- **你会一点 Python，但不熟悉 React**：你可以重点看 `App.tsx`、`api.ts`、组件状态和流式响应。
- **你知道大模型，但不熟悉 LangGraph**：你可以重点看 `KeeperState`、`StateGraph`、节点和边。
- **你想改造项目**：你可以看“常见修改任务应该改哪里”和“调试路线”。

阅读前建议先知道以下最基础概念：

- **浏览器**：运行 React 前端页面。
- **HTTP API**：前端通过 URL 请求后端，例如 `/coc/api/sessions`。
- **JSON**：前后端交换数据的主要格式。
- **数据库**：PostgreSQL 保存长期数据，例如角色、会话、回合日志。
- **向量数据库**：Chroma 保存文本向量，用来做相似检索，也就是 RAG。
- **LLM**：大语言模型，用来理解玩家输入、生成守秘人叙事。
- **LangGraph**：把一次复杂任务拆成多个节点，并按图结构依次执行。

## 1. 先用一句话理解本项目

`coc-lite` 是一个网页化的《克苏鲁的呼唤》AI 守秘人原型。

玩家在浏览器里输入行动，例如：

```text
我划向北岸码头，检查码头附近有没有脚印。
```

前端会把这句话发送给后端。后端的 `KeeperAgent` 会执行一整套流程：

```text
读取会话状态
  -> 理解玩家意图
  -> 检索剧本和规则资料
  -> 做规则裁定和骰点
  -> 调用 LLM 生成守秘人叙事
  -> 生成状态变化
  -> 防剧透和校验
  -> 写入数据库和记忆
  -> 返回前端显示
```

这条链路就是本项目最重要的主线。

## 2. 推荐阅读顺序

代码里已经加入了 `【阅读顺序 N】` 注释。建议按这个顺序看：

| 顺序 | 文件 | 适合理解什么 |
|---|---|---|
| 1 | `frontend/src/App.tsx` | 页面如何展示，玩家如何输入行动，状态如何刷新 |
| 2 | `frontend/src/api.ts` | 前端如何调用后端 API，如何读取流式响应 |
| 3 | `backend/app/main.py` | FastAPI 应用如何启动，路由如何挂载到 `/coc` |
| 4 | `backend/app/api.py` | 后端 API 如何接收前端请求，如何调用 `KeeperAgent` |
| 5 | `backend/app/services/agent.py` | LangGraph 守秘人核心，完整回合流程 |
| 6 | `backend/app/services/story_state.py` | 剧情状态如何初始化、增量更新、长期保存 |
| 7 | `backend/app/services/prompt_config.py` | 发送给 LLM 的提示词如何组织 |

如果你是完全初学者，不建议一开始就从 `agent.py` 读起。  
更好的路线是：

```text
先看页面按钮如何触发请求
  -> 再看请求发到哪个 API
  -> 再看 API 调用哪个 Agent 方法
  -> 最后看 Agent 内部节点如何流转
```

## 4. Web 初学者先看：一次页面操作发生了什么

以“玩家输入行动并发送”为例。

### 4.1 页面上发生的事

文件：`frontend/src/App.tsx`

用户在输入框中输入内容，然后点击发送。核心函数是：

```text
send(message)
```

它做了几件事：

1. 去掉输入前后的空格。
2. 检查当前是否有会话、是否正在忙。
3. 把玩家消息追加到 `messages`。
4. 再追加一条空的守秘人消息。
5. 调用 `api.streamAction(...)`。
6. 接收后端流式返回的事件。
7. 不断把 `chunk` 事件追加到最后一条守秘人消息。
8. 收到 `final` 事件后，刷新完整会话状态、选项、线索、物品栏等。

### 4.2 为什么先追加一条空的守秘人消息

前端想实现“守秘人正在逐段讲述”的效果。

所以它不是等后端全部完成后再显示，而是：

```text
玩家消息：我检查灯塔门口。
守秘人消息：
```

然后后端每返回一小段文字，就把这段文字拼到最后一条守秘人消息上。

最终可能变成：

```text
玩家消息：我检查灯塔门口。
守秘人消息：你踩着湿滑的石阶靠近灯塔门口，木门在风中微微震动……
```

### 4.3 前端主要状态变量

文件：`frontend/src/App.tsx`

| 状态 | 类型直觉 | 作用 |
|---|---|---|
| `characters` | 角色列表 | 后端返回的预设调查员 |
| `savedSessions` | 会话列表 | 历史存档 |
| `selectedCharacter` | 字符串 ID | 当前选择的角色 |
| `session` | 当前会话对象 | 页面右侧状态栏主要数据来源 |
| `messages` | 聊天消息数组 | 中间聊天区展示内容 |
| `options` | 字符串数组 | 下一步行动按钮 |
| `input` | 字符串 | 输入框内容 |
| `busy` | 布尔值 | 是否正在请求后端 |
| `status` | 字符串 | 页面顶部状态提示 |
| `error` | 字符串 | 错误提示 |
| `showGuide` | 布尔值 | 是否显示新手引导 |
| `showCharacterDialog` | 布尔值 | 是否显示角色选择弹窗 |

React 初学者可以重点理解：

```text
页面显示什么，主要由 useState 保存的数据决定。
调用 setXxx(...) 改变状态后，React 会重新渲染页面。
```

### 4.4 前端如何调用后端

文件：`frontend/src/api.ts`

`App.tsx` 不直接写 `fetch(...)`，而是调用 `api.ts` 中封装好的方法：

| 前端方法 | 后端接口 | 用途 |
|---|---|---|
| `api.characters()` | `GET /coc/api/characters` | 获取角色列表 |
| `api.sessions()` | `GET /coc/api/sessions` | 获取历史会话列表 |
| `api.getSession(id)` | `GET /coc/api/sessions/{id}` | 恢复指定会话 |
| `api.createSession(characterId)` | `POST /coc/api/sessions` | 创建新会话 |
| `api.deleteSession(id)` | `DELETE /coc/api/sessions/{id}` | 删除会话 |
| `api.sendAction(id, message)` | `POST /coc/api/sessions/{id}/actions` | 非流式提交行动 |
| `api.streamAction(id, message, onEvent)` | `POST /coc/api/sessions/{id}/actions/stream` | 流式提交行动 |

### 4.5 什么是 NDJSON 流式响应

普通 JSON 响应一般是这样：

```json
{
  "narration": "完整的一大段叙事文本"
}
```

前端必须等整个响应结束，才能解析它。

NDJSON 是“一行一个 JSON”：

```json
{"type":"start"}
{"type":"chunk","content":"你靠近灯塔门口，"}
{"type":"chunk","content":"潮湿的木门发出低沉声响。"}
{"type":"final","response":{...完整结果...}}
```

好处是：

- 后端可以边生成边返回。
- 前端可以边收到边显示。
- 用户感觉系统响应更快。

本项目的 `streamRequest` 会不断读取后端数据，把每一行 JSON 解析成事件，再交给 `App.tsx` 处理。

## 5. FastAPI 初学者先看：后端 API 是怎样接住请求的

### 5.1 后端入口

文件：`backend/app/main.py`

这个文件主要做应用级配置：

1. 创建 `FastAPI` 应用。
2. 注册数据库异常处理。
3. 注册 LLM 异常处理。
4. 配置 CORS。
5. 挂载静态资源路径 `/coc/assets`。
6. 挂载业务 API 路由 `/coc/api`。

注意：

```text
api.py 中 router 的 prefix 是 /api
main.py 中 include_router 的 prefix 是 /coc
最终路径就是 /coc/api
```

也就是说：

```text
APIRouter(prefix="/api") + app.include_router(..., prefix="/coc")
= /coc/api
```

### 5.2 API 文件

文件：`backend/app/api.py`

这个文件负责把 HTTP 请求转成 Python 函数调用。

常见接口：

| 方法 | 路径 | 函数 | 用途 |
|---|---|---|---|
| `GET` | `/coc/api/health` | `health` | 健康检查 |
| `POST` | `/coc/api/init` | `initialize_database` | 创建数据库表 |
| `POST` | `/coc/api/import` | `import_content` | 导入剧本、规则、角色 |
| `GET` | `/coc/api/characters` | `list_characters` | 查询角色 |
| `POST` | `/coc/api/sessions` | `create_session` | 创建会话 |
| `GET` | `/coc/api/sessions` | `list_sessions` | 查询会话列表 |
| `GET` | `/coc/api/sessions/{session_id}` | `get_session` | 查询单个会话 |
| `DELETE` | `/coc/api/sessions/{session_id}` | `delete_session` | 删除会话 |
| `POST` | `/coc/api/sessions/{session_id}/actions` | `submit_action` | 非流式行动 |
| `POST` | `/coc/api/sessions/{session_id}/actions/stream` | `submit_action_stream` | 流式行动 |

### 5.3 API 如何调用 Agent

非流式接口中有一行非常关键：

```text
result = get_agent().run_turn(db, session_id, payload.message)
```

流式接口中也会调用同样的核心方法：

```text
result = get_agent().run_turn(db, session_id, payload.message)
```

所以你可以这样理解：

```text
api.py 负责接收 HTTP 请求。
agent.py 负责真正处理玩家行动。
```

### 5.4 为什么有 get_agent 单例

`KeeperAgent` 初始化时会创建：

- LLM 客户端。
- Chroma 检索服务。
- LangGraph 编译后的图。

这些对象没有必要每个请求都重新创建。

所以项目使用 `_agent` 变量缓存一个实例：

```text
第一次请求：创建 KeeperAgent
后续请求：复用同一个 KeeperAgent
```

这就是一个简单的进程内单例。

## 6. LangGraph 初学者重点：什么是 KeeperState

文件：`backend/app/services/agent.py`

### 6.1 LangGraph 的最小理解模型

你可以先把 LangGraph 理解成：

```text
一张流程图 + 一个共享字典
```

- **流程图**：定义先执行哪个函数，再执行哪个函数。
- **共享字典**：每个函数都可以从里面读取上一步结果，也可以写入自己的结果。

在本项目中：

- 流程图是 `StateGraph(KeeperState)`。
- 共享字典是 `KeeperState`。
- 节点函数是 `load_state`、`parse_intent`、`retrieve_context` 等。

### 6.2 KeeperState 是什么

`KeeperState` 是一个 `TypedDict`。

初学者可以先忽略 `TypedDict` 的高级用法，只把它理解成“带类型提示的 dict”。

它保存一次玩家行动处理中产生的所有中间数据。

例如玩家输入：

```text
我检查码头附近有没有脚印。
```

执行过程中，`KeeperState` 会逐步变成这样：

```text
一开始：
{
  db,
  session_id,
  player_input
}

load_state 后：
{
  db,
  session_id,
  player_input,
  session,
  character,
  story_state
}

parse_intent 后：
{
  ...,
  intent: { action_type, target, skill, needs_clarification }
}

retrieve_context 后：
{
  ...,
  scenario_context,
  rule_context,
  entity_context,
  clue_context,
  memory_context
}

roll_tools 后：
{
  ...,
  dice_results,
  skill_checks,
  sanity_checks
}

commit_state 后：
{
  ...,
  narration,
  options,
  state_delta,
  discovered_clues
}
```

### 6.3 KeeperState 关键字段解释

| 字段 | 来自哪里 | 用途 |
|---|---|---|
| `db` | FastAPI 依赖注入 | 数据库会话，用来查询和写入 PostgreSQL |
| `session_id` | 前端 URL | 当前游戏会话 ID |
| `player_input` | 前端请求体 | 玩家本回合输入的自然语言 |
| `session` | `load_state` | 当前游戏会话对象 |
| `character` | `load_state` | 当前调查员角色 |
| `story_state` | `load_state` | 结构化剧情状态 |
| `intent` | `parse_intent` | LLM 或启发式规则解析出的行动意图 |
| `scenario_context` | `retrieve_context` | 从剧本向量库检索到的片段 |
| `rule_context` | `retrieve_context` | 从规则书向量库检索到的片段 |
| `entity_context` | `retrieve_context` | 地点、NPC、物品等结构化实体 |
| `clue_context` | `retrieve_context` | 线索索引检索结果 |
| `memory_context` | `retrieve_context` | 当前会话历史记忆 |
| `adjudication` | `adjudicate` | 本回合规则裁定结果 |
| `dice_results` | `roll_tools` | 掷骰结果 |
| `skill_checks` | `roll_tools` | 技能检定结果 |
| `sanity_checks` | `roll_tools` | 理智检定结果 |
| `resolution` | `resolve_action` | 对裁定和结果的汇总 |
| `generated_payload` | `generate_response` | LLM 原始 JSON 输出 |
| `narration` | `generate_response` | 玩家可见叙事 |
| `options` | `generate_next_options` | 下一步行动选项 |
| `state_delta` | `generate_state_delta` | 本回合造成的状态变化 |
| `validation_report` | `validate_state_delta_node` | 状态校验报告 |
| `leak_report` | `secret_leak_check` | 防剧透检查报告 |
| `audit` | `generate_next_options` | 审计信息，前端调试面板会显示摘要 |
| `discovered_clues` | `commit_state` | 本回合实际写入数据库的线索 |
| `needs_clarification` | `parse_intent` | 是否需要追问玩家 |

## 7. LangGraph 核心：图是怎样构建的

### 7.1 创建图

文件：`backend/app/services/agent.py`

`_build_graph` 中创建图：

```text
graph = StateGraph(KeeperState)
```

含义：

```text
这张图运行时，每个节点接收和返回的状态都是 KeeperState。
```

### 7.2 注册节点

项目用 `add_node` 注册节点：

```text
graph.add_node("load_state", self.load_state)
graph.add_node("parse_intent", self.parse_intent)
...
```

你可以理解为：

```text
给一个 Python 函数起一个图中的名字。
```

例如：

```text
节点名：load_state
实际执行函数：self.load_state
```

### 7.3 设置入口

```text
graph.set_entry_point("load_state")
```

表示每次图开始运行时，第一步执行 `load_state`。

### 7.4 添加普通边

```text
graph.add_edge("load_state", "parse_intent")
```

意思是：

```text
load_state 执行完，接着执行 parse_intent。
```

### 7.5 添加条件边

```text
graph.add_conditional_edges(
    "parse_intent",
    self.route_after_intent,
    {"clarify": "clarify_action", "continue": "retrieve_context"}
)
```

意思是：

1. `parse_intent` 执行完。
2. 调用 `route_after_intent(state)`。
3. 如果返回 `clarify`，进入 `clarify_action`。
4. 如果返回 `continue`，进入 `retrieve_context`。

这就是 LangGraph 的分支能力。

### 7.6 编译图

```text
return graph.compile()
```

编译后会得到可执行图。之后 `run_turn` 通过：

```text
self.graph.invoke(initial)
```

启动一次完整流程。

## 8. KeeperAgent 的 12 个节点详解

### 8.1 总览

```text
load_state
  -> parse_intent
      -> 如果模糊：clarify_action -> commit_state -> END
      -> 如果清晰：retrieve_context
  -> adjudicate
  -> roll_tools
  -> resolve_action
  -> generate_response
  -> generate_state_delta
  -> validate_state_delta
  -> secret_leak_check
  -> generate_next_options
  -> commit_state
  -> END
```

### 8.2 节点 1：load_state

职责：从数据库读取当前会话及相关对象。

读取内容包括：

- 当前会话 `GameSession`。
- 当前角色 `Character`。
- 已发现线索 `Clue`。
- 当前物品 `InventoryItem`。
- 剧情 Flag `StoryFlag`。
- 最近回合日志 `TurnLog`。

为什么要先做这一步？

因为后面节点都依赖当前状态。例如：

- 规则裁定需要角色技能。
- RAG 检索需要当前位置和当前场景。
- 防剧透需要知道玩家已经发现了哪些线索。
- 状态提交需要知道当前时间、地点、危险等级。

### 8.3 节点 2：parse_intent

职责：把玩家自然语言转成结构化行动意图。

玩家可能输入：

```text
我过去看看。
```

这句话很模糊，系统可能不知道“过去”是去哪里，“看看”是看什么。

玩家也可能输入：

```text
我检查灯塔门口的脚印。
```

这就比较清晰，可以解析成：

```json
{
  "action_type": "调查",
  "target": "灯塔门口的脚印",
  "skill": "侦查",
  "needs_clarification": false
}
```

该节点会调用：

- `heuristic_intent(message)`：启发式兜底。
- `build_intent_prompt(...)`：构造提示词。
- `self.llm.chat_json(...)`：调用 LLM，并要求返回 JSON。

为什么需要兜底？

因为 LLM 可能：

- 没配置。
- 请求失败。
- 输出不是合法 JSON。

此时系统不能直接崩溃，所以用启发式结果继续运行。

### 8.4 条件分支：route_after_intent

职责：根据 `needs_clarification` 决定下一步。

```text
needs_clarification = true
  -> clarify_action

needs_clarification = false
  -> retrieve_context
```

这一步体现了 LangGraph 的价值：

```text
同一张图可以根据状态走不同路线。
```

### 8.5 节点 3A：clarify_action

职责：如果玩家输入太模糊，就不推进剧情，只追问。

例如玩家输入：

```text
我看看。
```

系统可能回复：

```text
你想具体调查哪里，或以什么方式行动？
```

这个节点会设置：

- `narration`：追问文本。
- `options`：几个可选行动。
- `state_delta`：标记这是澄清，不推进时间和危险。

然后直接进入 `commit_state`。

### 8.6 节点 3B：retrieve_context

职责：从 Chroma 向量库中检索本回合需要的资料。

它会构造一个查询文本，大致包含：

- 当前地点。
- 当前场景。
- 玩家输入。
- 行动目标。
- 可能相关技能。

然后分别查询：

| 集合 | 字段 | 内容 |
|---|---|---|
| `scenario_chunks` | `scenario_context` | 剧本文本分块 |
| `scenario_entities` | `entity_context` | 地点、NPC、物品等实体 |
| `clue_index` | `clue_context` | 线索索引 |
| `session_memory_chunks` | `memory_context` | 当前会话长期记忆 |
| `rule_chunks` | `rule_context` | 规则书片段 |

RAG 初学者可以这样理解：

```text
LLM 本身不知道本项目剧本细节。
所以后端先从资料库里找相关片段，再把这些片段放进 prompt，让 LLM 基于资料回答。
```

### 8.7 节点 4：adjudicate

职责：判断玩家行动是否需要规则裁定。

例如：

- 普通观察：可能不需要掷骰。
- 搜索脚印：可能需要 `侦查`。
- 说服 NPC：可能需要 `说服`。
- 潜行接近怪物：可能需要 `潜行`。

该节点会调用：

```text
adjudicate_action(...)
```

输出 `adjudication`，里面可能包含：

- 是否需要技能检定。
- 技能名称。
- 难度。
- 风险等级。
- 耗时。
- 是否需要理智检定。
- 裁定理由。

### 8.8 节点 5：roll_tools

职责：执行真正的骰点和检定。

重要原则：

```text
骰点结果不能让 LLM 自己编。
```

原因很简单：

- LLM 生成的数字不是真随机。
- LLM 可能为了叙事效果随意改变结果。
- 跑团规则要求骰点结果可信。

所以本项目用规则工具生成：

- `dice_results`
- `skill_checks`
- `sanity_checks`

后面的 LLM 只能基于这些结果写叙事。

### 8.9 节点 6：resolve_action

职责：把规则结果整理成“裁定摘要”。

它会把：

- 技能检定结果。
- 理智检定结果。
- 是否偏离剧情。
- 裁定依据。

整理成 `resolution`。

这个结果会给后续 LLM 参考。

### 8.10 节点 7：generate_response

职责：调用 LLM 生成守秘人回应。

该节点会准备很多上下文：

- 当前地点。
- 当前场景。
- 角色职业和状态。
- 玩家输入。
- 行动意图。
- 规则裁定。
- 检定结果。
- 物品栏。
- 剧本片段。
- 实体片段。
- 线索片段。
- 会话记忆。
- 规则片段。

然后调用：

```text
build_keeper_response_prompt(...)
self.llm.chat_json(...)
```

LLM 需要返回 JSON，主要字段是：

- `narration`：玩家可见叙事。
- `options`：下一步行动选项。
- `state_delta`：建议状态变化。
- `discovered_clues`：本回合发现线索。

注意：

```text
generate_response 不直接写数据库。
```

它只是生成内容和建议变化。真正落库在最后的 `commit_state`。

### 8.11 节点 8：generate_state_delta

职责：把 LLM 的自由格式状态建议整理成稳定结构。

为什么需要这一步？

因为 LLM 输出可能不稳定，例如：

```json
{
  "state_delta": {
    "当前位置": "码头",
    "耗时": "十分钟"
  }
}
```

也可能输出：

```json
{
  "state_delta": {
    "location": "码头",
    "time_cost_minutes": 10
  }
}
```

后端不能到处兼容各种格式，所以集中用 `build_turn_delta` 整理。

整理后得到内部统一的 `state_delta`。

### 8.12 节点 9：validate_state_delta

职责：校验状态变化。

项目不能完全相信 LLM 的 `state_delta`，因为它可能：

- 编造不存在的地点。
- 让危险等级变化过大。
- 写入不合理字段。
- 输出结构不符合预期。

所以写入数据库前要先经过 `validate_state_delta`。

### 8.13 节点 10：secret_leak_check

职责：防止剧透。

克苏鲁跑团中，玩家不能提前知道：

- 幕后真相。
- NPC 真实身份。
- 怪物真名。
- 隐藏地点。
- 主持人秘密说明。

所以玩家可见的：

- `narration`
- `options`

会经过清洗。

### 8.14 节点 11：generate_next_options

职责：整理下一步行动按钮。

它会：

- 保留 LLM 给出的选项。
- 去重。
- 限制数量。
- 在需要时追加引导选项。
- 始终保留“自定义行动”。

这样前端可以直接渲染按钮。

### 8.15 节点 12：commit_state

职责：集中提交所有副作用。

这是非常重要的设计点：

```text
前面节点主要是在 KeeperState 里准备数据。
commit_state 才真正写数据库、写记忆、创建线索、更新物品。
```

它会做：

1. 应用理智检定结果。
2. 调用 `apply_turn_delta` 更新剧情状态。
3. 更新当前地点、场景、时间、危险等级。
4. 写入新发现线索。
5. 应用物品变化。
6. 更新无新线索计数。
7. 生成回合摘要。
8. 写入 `TurnLog`。
9. 写入 Chroma 会话长期记忆。
10. `db.commit()` 保存数据库。

## 9. 剧情状态 story_state 是什么

文件：`backend/app/services/story_state.py`

### 9.1 为什么需要 story_state

数据库中的 `GameSession` 已经有：

- `current_location`
- `current_scene`
- `current_time`
- `danger_level`

但跑团状态远不止这些。

还需要保存：

- 已访问地点。
- 当前可前往地点。
- 已发现线索。
- 未解析线索。
- 已调查对象。
- 当前危险。
- 玩家最近行动。
- 剧情 flag。
- 仪式进度。
- 时间压力。
- 敌对势力警觉。

这些都放在 `session.state` 这个 JSONB 字段中。

`story_state.py` 就是专门维护这个结构的。

### 9.2 三个核心函数

| 函数 | 作用 |
|---|---|
| `ensure_story_state` | 保证状态结构完整 |
| `build_turn_delta` | 构造本回合变化 |
| `apply_turn_delta` | 把本回合变化合并进长期状态 |

### 9.3 ensure_story_state

作用：

```text
不管旧状态缺什么字段，都补成统一结构。
```

为什么需要？

因为：

- 旧存档可能没有新字段。
- 新会话一开始是空状态。
- LLM 状态变更可能缺字段。

有了它，后面代码就可以放心访问：

```text
state["剧情"]
state["场景"]
state["记忆"]
state["秘密"]
```

### 9.4 build_turn_delta

作用：

```text
根据本回合输入、意图、裁定、检定和 LLM 输出，整理出标准变化。
```

它不会直接写数据库。

你可以把它理解成：

```text
本回合变化草稿整理器
```

### 9.5 apply_turn_delta

作用：

```text
把 state_delta 应用到 story_state 上。
```

它会更新：

- 当前地点。
- 当前场景。
- 当前时间。
- 危险等级。
- 已访问地点。
- 可前往地点。
- 已调查对象。
- 最近行动。
- 重要裁定记录。

最终结果会保存在 `session.state`。

## 10. RAG 是如何工作的

### 10.1 RAG 的一句话解释

RAG 是 Retrieval-Augmented Generation，中文常译为“检索增强生成”。

简单说：

```text
先从资料库找相关内容，再让 LLM 基于这些内容回答。
```

### 10.2 本项目为什么需要 RAG

因为守秘人要参考：

- 《无光的灯塔》剧本。
- 守秘人规则书。
- 调查员手册。
- 结构化地点/NPC/物品。
- 当前会话已经发生过的事情。

这些内容不应该全部塞进每次 prompt。

原因：

- 文本太长。
- 成本高。
- LLM 容易抓不住重点。
- 可能增加剧透风险。

所以项目先把资料切块、向量化、存进 Chroma。每次玩家行动时，只检索最相关的一小部分。

### 10.3 Chroma 集合

文件：`backend/app/services/retrieval.py`

本项目常用集合：

| 集合名 | 内容 | 何时使用 |
|---|---|---|
| `scenario_chunks` | 剧本文本分块 | 生成叙事、判断场景事实 |
| `rule_chunks` | 规则书分块 | 行动裁定、规则说明 |
| `scenario_entities` | 地点、NPC、物品等结构化实体 | 推断当前位置和可前往地点 |
| `clue_index` | 线索索引 | 判断是否发现新线索 |
| `session_memory_chunks` | 当前会话长期记忆 | 让后续回合记得玩家经历 |

### 10.4 Embedding 是什么

Embedding 是把文本变成数字向量。

例如：

```text
"灯塔门口的脚印" -> [0.12, -0.03, 0.77, ...]
```

相似意思的文本，向量距离会更近。

所以当玩家输入：

```text
我检查码头有没有痕迹
```

系统可以找到与“码头”“痕迹”“脚印”“登陆点”等相关的剧本片段。

### 10.5 两个数据库的工作逻辑：PostgreSQL 与 Chroma

本项目同时使用两个数据库：

- **PostgreSQL**：关系型数据库，负责保存“游戏事实”和“业务状态”。
- **Chroma**：向量数据库，负责保存“可被语义检索的文本资料”和“会话记忆”。

最重要的一句话是：

```text
PostgreSQL 回答：现在这局游戏真实发生了什么？
Chroma 回答：哪些文本资料和当前玩家行动语义最相关？
```

也可以这样理解：

```text
PostgreSQL = 存档系统
Chroma = 资料检索系统
```

#### 10.5.1 为什么不能只用一个数据库

如果只用 PostgreSQL：

- 可以稳定保存角色、会话、线索、物品。
- 但它不擅长回答“哪几段剧本文本和玩家这句话最相似”。
- 用普通 SQL `LIKE` 搜索很难理解同义词和语义接近的表达。

如果只用 Chroma：

- 可以按语义找相似文本。
- 但它不适合维护复杂业务关系，例如会话属于哪个角色、线索是否重复、物品数量是多少。
- 它也不适合作为页面右侧状态栏的权威存档来源。

所以本项目把职责拆开：

| 数据库 | 主要职责 | 典型问题 |
|---|---|---|
| PostgreSQL | 精确保存结构化游戏状态 | 当前角色是谁？当前位置是哪？已发现哪些线索？物品栏有什么？ |
| Chroma | 按语义检索相关文本 | 玩家说“检查痕迹”时，哪些剧本片段、规则片段、历史记忆最相关？ |

#### 10.5.2 两个数据库分别存什么

PostgreSQL 保存的是结构化数据。

对应文件：

- `backend/app/models.py`
- `backend/app/database.py`
- `backend/app/api.py`
- `backend/app/services/agent.py`

主要表：

| 表 | 保存内容 | 是否直接影响前端显示 |
|---|---|---|
| `scenarios` | 剧本基本信息 | 间接影响 |
| `characters` | 预设调查员 | 是 |
| `sessions` | 当前会话、地点、场景、时间、剧情状态 JSON | 是 |
| `turn_logs` | 每回合输入、检索、骰点、叙事、状态变化 | 调试时影响 |
| `clues` | 玩家已发现线索 | 是 |
| `inventory_items` | 当前物品栏 | 是 |
| `story_flags` | 剧情标记 | 是 |

Chroma 保存的是文本向量。

对应文件：

- `backend/app/services/retrieval.py`
- `backend/app/services/importer.py`
- `backend/app/services/chunking.py`
- `backend/app/services/content_index.py`
- `backend/app/services/llm.py`
- `backend/app/services/agent.py`

主要集合：

| 集合 | 保存内容 | 什么时候用 |
|---|---|---|
| `scenario_chunks` | 剧本文本切块后的向量 | 生成守秘人叙事时检索剧本事实 |
| `rule_chunks` | 规则书文本切块后的向量 | 需要规则裁定时检索规则资料 |
| `scenario_entities` | 地点、NPC、物品等实体索引 | 判断当前位置、可见地点、相关实体 |
| `clue_index` | 线索索引 | 判断玩家行动是否可能发现线索 |
| `session_memory_chunks` | 当前会话每回合摘要和长期记忆 | 后续回合回忆玩家过去做过什么 |

#### 10.5.3 初始化和导入阶段：两个数据库分别做什么

初始化接口：

```text
POST /coc/api/init
```

这一步主要影响 PostgreSQL。

流程是：

```text
api.py
  -> initialize_database
  -> init_db
  -> Base.metadata.create_all
  -> PostgreSQL 中创建表
```

它只是建表，不负责把剧本和规则书放进 Chroma。

导入接口：

```text
POST /coc/api/import
```

这一步会同时影响 PostgreSQL 和 Chroma。

流程可以拆成两条线：

```text
导入剧本基本信息和角色
  -> 写入 PostgreSQL

切分剧本、规则书、实体、线索索引
  -> 生成 Embedding
  -> 写入 Chroma
```

更具体地说：

1. `import_default_content` 会先检查 PostgreSQL 中是否已有《无光的灯塔》这个 `Scenario`。
2. 如果没有，就在 PostgreSQL 的 `scenarios` 表中创建一条剧本记录。
3. 如果启用角色导入，就把预设人物卡导入 PostgreSQL 的 `characters` 表。
4. 后端读取剧本文档，把 Markdown 切成多个 `scenario_chunks`。
5. 后端提取结构化地点、NPC、物品等，写入 `scenario_entities`。
6. 后端提取线索索引，写入 `clue_index`。
7. 后端读取规则书，切成多个 `rule_chunks`。
8. 这些文本块会通过 Embedding 模型转成向量，再 upsert 到 Chroma。

所以导入完成后：

```text
PostgreSQL 中有：剧本记录、角色记录。
Chroma 中有：剧本文本向量、规则文本向量、实体向量、线索索引向量。
```

#### 10.5.4 PostgreSQL 为什么也要保存剧本相关信息

看到这里你可能会有一个疑问：

```text
既然剧本文本已经切块后放进 Chroma，
为什么 PostgreSQL 里还需要 scenarios 这张表？
```

原因是：PostgreSQL 保存的不是“用于语义检索的完整剧本文本”，而是“业务系统需要精确引用的剧本身份信息”。

可以这样区分：

| 内容 | 更适合放在哪里 | 原因 |
|---|---|---|
| 剧本名称，例如《无光的灯塔》 | PostgreSQL | 需要精确查询、关联角色和会话 |
| 剧本文件路径 | PostgreSQL | 导入、管理和排查时需要知道来源 |
| 剧本时代、地点等元数据 | PostgreSQL | 页面展示、会话创建、筛选时需要结构化字段 |
| 剧本文本正文 | Chroma | 太长，更适合切块后做语义检索 |
| 剧本地点/NPC/线索片段 | Chroma | 玩家行动时需要按语义召回相关片段 |

也就是说：

```text
PostgreSQL 中的 Scenario 是“剧本档案卡”。
Chroma 中的 scenario_chunks 是“剧本正文资料库”。
```

这个设计有几个实际好处。

第一个好处是：会话和角色需要有稳定归属。

`GameSession` 里有 `scenario_id`，`Character` 里也有 `scenario_id`。  
这表示：

```text
这个会话属于哪个剧本？
这个角色属于哪个剧本？
```

如果将来项目支持多个剧本，例如：

```text
无光的灯塔
鬼屋
边缘之地
```

那么 PostgreSQL 可以很清楚地保存：

```text
会话 A 属于《无光的灯塔》
会话 B 属于《鬼屋》
角色 X 属于《无光的灯塔》
角色 Y 属于《边缘之地》
```

第二个好处是：业务查询需要精确匹配。

例如导入时，代码会先检查：

```text
PostgreSQL 里是否已经存在名为“无光的灯塔”的 Scenario？
```

如果存在，就复用它。  
如果不存在，就创建一条新的 `Scenario` 记录。

这种“是否已经存在某个剧本”的判断，适合用 PostgreSQL 做，因为它需要精确匹配，而不是语义相似。

第三个好处是：Chroma 负责检索，不适合作为权威业务索引。

Chroma 擅长回答：

```text
哪些文本和“灯塔门口的脚印”最相似？
```

但它不适合作为唯一来源回答：

```text
当前系统有几个剧本？
某个角色属于哪个剧本？
某个会话应该加载哪个剧本？
删除某个剧本时要影响哪些会话？
```

这些问题需要稳定的主键、外键和关系约束，所以更适合 PostgreSQL。

第四个好处是：前端和 API 需要稳定 ID。

前端创建会话时，后端最终需要知道：

```text
创建的是哪个剧本下的会话？
使用的是哪个剧本下的角色？
```

这类数据不能依赖“向量相似度搜索”得到，而应该依赖明确的数据库 ID。

因此，两个数据库对剧本的分工是：

```text
PostgreSQL：
  保存剧本是谁、来自哪里、和哪些角色/会话有关。

Chroma：
  保存剧本内容是什么，并支持按玩家输入检索相关片段。
```

如果导入时选择 `reset_chroma=true`：

```text
只会清空并重建 Chroma 中的向量集合。
不会等同于清空 PostgreSQL 的所有业务表。
```

#### 10.5.5 创建会话阶段：主要写 PostgreSQL

创建会话接口：

```text
POST /coc/api/sessions
```

这一步主要写 PostgreSQL。

创建新会话时，后端会：

1. 选择一个角色。
2. 创建 `GameSession`。
3. 初始化当前位置、当前场景、当前时间、危险等级。
4. 初始化 `session.state` 中的剧情状态。
5. 同步角色初始物品到 `inventory_items`。

这时通常不会立刻向 Chroma 写入新的会话记忆。

原因是：

```text
新会话刚创建，还没有玩家行动，也就没有可总结的回合记忆。
```

#### 10.5.6 每次玩家行动前：先读 PostgreSQL，再查 Chroma

玩家提交行动后，后端进入 `KeeperAgent.run_turn`。

第一步是 `load_state`。

它读取 PostgreSQL：

```text
GameSession
Character
Clue
InventoryItem
StoryFlag
TurnLog
```

这一步的目的不是检索资料，而是确认“当前游戏真实状态”：

- 玩家当前在哪里？
- 当前是什么场景？
- 当前时间是多少？
- 角色当前 HP、SAN、物品是什么？
- 玩家已经发现了哪些线索？
- 最近几回合发生了什么？

接着进入 `retrieve_context`。

它查询 Chroma：

```text
scenario_chunks
scenario_entities
clue_index
session_memory_chunks
rule_chunks
```

这一步的目的不是读取存档，而是找到“和本回合最相关的文本”。

查询文本通常会结合：

- 玩家本回合输入。
- 当前地点。
- 当前场景。
- 解析出的行动目标。
- 推断出的技能。

例如玩家输入：

```text
我检查码头附近有没有脚印。
```

PostgreSQL 会告诉 Agent：

```text
当前地点：北岸码头
当前角色：调查局探员
已发现线索：旧船票、湿透的地图
物品栏：手电筒、左轮手枪
```

Chroma 会返回类似：

```text
和“码头”“脚印”“痕迹”“北岸”语义接近的剧本片段
和“侦查检定”相关的规则片段
和当前会话过去调查码头相关的记忆
```

两边结果合在一起，才会成为 LLM 的上下文。

#### 10.5.7 每次玩家行动后：PostgreSQL 记录事实，Chroma 记录记忆

一次 LangGraph 回合快结束时，会进入 `commit_state`。

这一步会同时写 PostgreSQL 和 Chroma，但写入内容不同。

PostgreSQL 写入的是权威事实：

| 写入内容 | 保存位置 |
|---|---|
| 当前地点、场景、时间、危险等级 | `sessions` |
| 结构化剧情状态 | `sessions.state` |
| 新发现线索 | `clues` |
| 物品变化 | `inventory_items` |
| 回合输入、意图、检索、骰点、回应、状态变化 | `turn_logs` |
| 剧情摘要 | `sessions.summary` |

Chroma 写入的是可检索记忆：

| 写入内容 | 保存位置 |
|---|---|
| 本回合玩家做了什么、守秘人如何回应、发生了什么结果 | `session_memory_chunks` |
| 当前会话摘要记忆 | `session_memory_chunks` |

为什么回合日志要放 PostgreSQL，而会话记忆还要放 Chroma？

因为二者用途不同：

```text
TurnLog 用来精确查看某一回合完整记录。
session_memory_chunks 用来让未来回合按语义找回相关经历。
```

例如第 3 回合玩家在码头发现了脚印。第 18 回合玩家又提到“之前岸边的痕迹”。  
如果只看最近几条 `TurnLog`，第 3 回合可能已经太远了。  
但 Chroma 可以通过“岸边”“痕迹”和“脚印”的语义相似性，把旧记忆重新找出来。

#### 10.5.8 删除会话时：两个数据库都要清理

删除会话接口：

```text
DELETE /coc/api/sessions/{session_id}
```

它会做两类清理：

1. 删除 PostgreSQL 中的 `GameSession`。
2. 同步删除 Chroma 中 `session_memory_chunks` 里对应 `session_id` 的会话记忆。

为什么要清理 Chroma？

因为如果只删 PostgreSQL，不删 Chroma，会出现这种问题：

```text
数据库里这局游戏已经不存在了。
但向量库里还残留这局游戏的记忆。
未来检索时可能把旧存档内容找出来。
```

这会污染新会话的上下文。

#### 10.5.9 前端主要相信谁

前端页面展示主要相信 PostgreSQL 返回的数据。

例如：

- 当前地点。
- 当前场景。
- 当前时间。
- 角色状态。
- 线索簿。
- 物品栏。
- 剧情状态。
- 回合历史。

这些都来自后端 API 返回的 `session`，而 `session` 本质上来自 PostgreSQL。

Chroma 的结果通常不会直接作为页面状态显示。

它主要作为 LLM 的参考资料：

```text
玩家不可直接看到 Chroma 原始检索结果。
LLM 会基于检索结果生成 narration。
后端再把 narration 和状态变化返回前端。
```

调试面板或 `TurnLog.retrieval` 可能会保存部分检索结果摘要，方便开发者排查问题。

#### 10.5.10 一次玩家行动中的两个数据库顺序图

```text
玩家输入行动
  ↓
FastAPI 接收请求
  ↓
KeeperAgent.run_turn
  ↓
load_state
  ↓
读取 PostgreSQL：会话、角色、线索、物品、历史回合
  ↓
parse_intent
  ↓
retrieve_context
  ↓
查询 Chroma：剧本、规则、实体、线索索引、会话记忆
  ↓
adjudicate / roll_tools / generate_response
  ↓
generate_state_delta / validate_state_delta / secret_leak_check
  ↓
commit_state
  ↓
写 PostgreSQL：状态、线索、物品、回合日志、摘要
  ↓
写 Chroma：本回合长期记忆和摘要记忆
  ↓
返回前端
```

#### 10.5.11 调试时如何判断问题出在哪个数据库

如果页面上的状态不对，优先查 PostgreSQL 相关逻辑。

例如：

- 角色没加载。
- 会话列表为空。
- 线索簿没显示。
- 物品栏没更新。
- 当前地点没有变化。
- 回合日志缺失。

优先看：

- `backend/app/models.py`
- `backend/app/api.py`
- `backend/app/services/agent.py` 的 `load_state` 和 `commit_state`
- `backend/app/services/story_state.py`

如果守秘人“不知道剧本内容”或“经常答非所问”，优先查 Chroma/RAG 相关逻辑。

例如：

- 明明剧本里有码头信息，守秘人却说不知道。
- 规则裁定缺少依据。
- 很久以前发生过的事，后续回合完全想不起来。
- 检索结果和玩家输入无关。

优先看：

- `backend/app/services/importer.py`
- `backend/app/services/chunking.py`
- `backend/app/services/content_index.py`
- `backend/app/services/retrieval.py`
- `backend/app/services/llm.py`
- `TurnLog.retrieval`

#### 10.5.12 最小总结

```text
PostgreSQL 是权威存档：
保存“已经发生、已经确认、需要精确展示”的游戏事实。

Chroma 是语义资料库：
保存“可以被相似度搜索召回”的剧本、规则、线索索引和会话记忆。

一次回合通常是：
先从 PostgreSQL 读当前事实，
再从 Chroma 找相关资料，
生成结果后把事实写回 PostgreSQL，
再把本回合摘要写进 Chroma，供未来检索。
```

## 11. 数据库模型如何理解

文件：`backend/app/models.py`

### 11.1 核心表

| 模型 | 表名 | 作用 |
|---|---|---|
| `Scenario` | `scenarios` | 剧本，例如《无光的灯塔》 |
| `Character` | `characters` | 预设调查员角色 |
| `GameSession` | `sessions` | 玩家一次游戏存档 |
| `TurnLog` | `turn_logs` | 每一回合的输入、检索、骰点、回应和状态变化 |
| `Clue` | `clues` | 玩家已发现线索 |
| `InventoryItem` | `inventory_items` | 当前会话物品栏 |
| `StoryFlag` | `story_flags` | 结构化剧情标记 |

### 11.2 最重要的是 GameSession

`GameSession` 表示一局游戏。

它保存：

- 当前角色。
- 当前地点。
- 当前场景。
- 当前时间。
- 危险等级。
- 剧情摘要。
- 结构化状态 `state`。

前端右侧状态栏大部分内容都来自当前 `session`。

### 11.3 TurnLog 是调试神器

每次玩家行动后，都会写入一条 `TurnLog`。

它包含：

- 玩家输入。
- 解析出的意图。
- 检索到的上下文。
- 裁定结果。
- 骰点结果。
- 守秘人回应。
- 状态变化。

如果你想调试“为什么守秘人这么回答”，应该优先看 `turn_logs`。

## 12. 提示词 prompt 如何理解

文件：`backend/app/services/prompt_config.py`

### 12.1 为什么提示词单独放一个文件

这样做有几个好处：

- 业务代码更清晰。
- 调整模型行为时不用改 Agent 流程。
- 可以集中维护输出格式。
- 可以集中维护防剧透要求。

### 12.2 两类核心提示词

| 提示词 | 作用 |
|---|---|
| `INTENT_SYSTEM_PROMPT` | 告诉 LLM 如何解析玩家意图 |
| `KEEPER_RESPONSE_SYSTEM_PROMPT` | 告诉 LLM 如何生成守秘人回应 |

### 12.3 意图解析提示词

它要求 LLM 输出 JSON，字段包括：

- `action_type`
- `target`
- `skill`
- `needs_clarification`
- `clarification_question`
- `is_meta`
- `reason`

这样后续节点就不需要解析自然语言，而是处理结构化字段。

### 12.4 守秘人回应提示词

它要求 LLM 输出：

- `narration`
- `options`
- `state_delta`
- `discovered_clues`

并且要求：

- 不要剧透。
- 不要替玩家做重大决定。
- 不要重写骰点结果。
- 不要编造关键事实。
- 描写玩家可以感知到的内容。

## 13. 一次玩家行动的完整生命周期

下面用一个具体例子串起来。

玩家输入：

```text
我划向北岸码头，检查附近有没有脚印。
```

### 13.1 前端阶段

文件：`frontend/src/App.tsx`

1. 用户点击发送。
2. `send(message)` 被调用。
3. 前端追加玩家消息。
4. 前端追加空的守秘人消息。
5. 调用 `api.streamAction(session.id, message, onEvent)`。

### 13.2 API 封装阶段

文件：`frontend/src/api.ts`

1. 拼接 URL：`/coc/api/sessions/{id}/actions/stream`。
2. 使用 `fetch` 发送 POST 请求。
3. 请求体是：

```json
{
  "message": "我划向北岸码头，检查附近有没有脚印。"
}
```

4. 开始读取 NDJSON 流。

### 13.3 FastAPI 阶段

文件：`backend/app/api.py`

1. 请求进入 `submit_action_stream`。
2. 检查 `session_id` 是否存在。
3. 创建 `event_stream` 生成器。
4. 先返回 `start` 事件。
5. 调用 `get_agent().run_turn(...)`。

### 13.4 LangGraph 阶段

文件：`backend/app/services/agent.py`

图开始执行：

```text
load_state
  读取当前会话、角色、线索、物品

parse_intent
  解析为：移动 + 调查，目标是北岸码头/脚印，可能技能是侦查

route_after_intent
  判断输入清晰，进入 continue 分支

retrieve_context
  检索码头、脚印、北岸、剧本片段、规则片段、历史记忆

adjudicate
  判断是否需要侦查检定、耗时和风险

roll_tools
  如果需要检定，执行 D100 和技能检定

resolve_action
  汇总检定结果和裁定依据

generate_response
  调用 LLM 生成叙事、选项、状态变化建议

generate_state_delta
  整理本回合地点、场景、耗时、线索等变化

validate_state_delta
  校验状态变化是否合法

secret_leak_check
  清洗玩家可见叙事和选项，避免剧透

generate_next_options
  整理下一步按钮

commit_state
  写入数据库、线索、物品、回合日志和长期记忆
```

### 13.5 返回前端阶段

文件：`backend/app/api.py`

`event_stream` 会把叙事分块返回：

```json
{"type":"chunk","content":"你顶着海风划向北岸码头，"}
{"type":"chunk","content":"木桩间传来潮水拍击声。"}
```

最后返回完整结果：

```json
{
  "type": "final",
  "response": {
    "session": {...},
    "narration": "完整叙事",
    "options": ["检查脚印", "观察码头木屋", "自定义行动"],
    "dice_results": [...],
    "skill_checks": [...],
    "sanity_checks": [...],
    "discovered_clues": [...],
    "state_delta": {...},
    "needs_clarification": false
  }
}
```

### 13.6 页面更新阶段

文件：`frontend/src/App.tsx`

1. `chunk` 到达时，前端调用 `appendToLastKeeperMessage`。
2. `final` 到达时，前端调用 `applyActionResponse`。
3. 页面更新：
   - 聊天区显示完整叙事。
   - 下一步按钮刷新。
   - 右侧状态栏刷新。
   - 线索簿刷新。
   - 物品栏刷新。
   - 调试信息刷新。

## 16. 初学者容易混淆的概念

### 16.1 session 和 state

`session` 是数据库中的一局游戏。

`session.state` 是这局游戏里的结构化 JSON 状态。

可以理解为：

```text
session = 存档盒子
session.state = 存档盒子里的复杂剧情记录
```

### 16.2 KeeperState 和 story_state

`KeeperState`：

```text
一次 LangGraph 执行中的临时工作台。
```

`story_state`：

```text
长期保存到数据库中的剧情状态。
```

区别：

| 项 | 生命周期 | 是否长期保存 |
|---|---|---|
| `KeeperState` | 一次玩家行动 | 否，主要是运行时中间数据 |
| `story_state` | 整个会话 | 是，保存到 `session.state` |

### 16.3 narration 和 keeper_response

`narration` 是本回合 Agent 生成的守秘人叙事。

`keeper_response` 是写入 `TurnLog` 后的字段名。

可以理解为：

```text
运行时叫 narration
落库日志里叫 keeper_response
```

### 16.4 options 和玩家输入

`options` 是系统推荐按钮，不限制玩家只能选这些。

玩家仍然可以输入自定义行动。

### 16.5 Chroma 和 PostgreSQL

更完整的工作流程可以回看 `10.5 两个数据库的工作逻辑：PostgreSQL 与 Chroma`。

PostgreSQL 保存结构化游戏数据：

- 会话。
- 角色。
- 线索。
- 物品。
- 回合日志。

Chroma 保存用于语义检索的文本向量：

- 剧本片段。
- 规则片段。
- 会话记忆。

简单说：

```text
PostgreSQL 负责“事实存档”。
Chroma 负责“相似文本检索”。
```

### 17.2 为什么 API Key 不能写进代码

API Key 是访问模型服务的凭证。

如果写进代码：

- 容易提交到 Git。
- 容易泄露给别人。
- 可能产生费用风险。

所以本项目通过 `.env` 配置。

### 17.3 LLM 未配置时会怎样

`backend/app/services/llm.py` 中有兜底逻辑。

如果聊天模型没有配置：

- `chat_text` 返回空字符串。
- `chat_json` 返回 fallback。

也就是说，部分流程仍可运行，但智能叙事能力会明显下降。

如果 Embedding 没配置：

- `EmbeddingClient` 会使用 `fallback_embedding`。
- 这可以保证系统不立刻崩溃。
- 但真实语义检索效果会不如正式 Embedding 模型。

## 20. 常见问题

### 20.1 为什么前端 API 路径不是直接 `/api`

因为项目部署在 `/coc` 子路径下。

最终后端路径是：

```text
/coc/api/...
```

前端使用：

```text
import.meta.env.BASE_URL
```

来自动拼接基础路径。

### 20.2 为什么需要流式接口

如果只用普通接口，玩家要等完整回合执行完才能看到文本。

流式接口可以先显示叙事片段，提高响应体验。

### 20.3 为什么 LLM 要输出 JSON

因为后端需要稳定读取字段。

如果让 LLM 输出自然语言，后端很难可靠判断：

- 叙事是哪部分。
- 选项是哪部分。
- 状态变化是哪部分。
- 线索是哪部分。

JSON 可以让后续代码更稳定。

### 20.4 为什么还要校验 LLM 输出

因为 LLM 可能不稳定。

它可能：

- 输出非法 JSON。
- 编造地点。
- 泄露秘密。
- 给出过大的状态变化。
- 产生格式不一致的字段。

所以本项目使用 fallback、状态校验、防剧透过滤来降低风险。

### 20.5 为什么有 PostgreSQL 又有 Chroma

它们解决的问题不同。

PostgreSQL：

```text
精确保存结构化事实。
```

Chroma：

```text
根据语义相似度查找相关文本。
```

两者互补，不是替代关系。

## 21. 最小心智模型总结

如果你读完还是觉得信息很多，请记住下面这张最小图：

```text
App.tsx
  玩家输入行动
  ↓
api.ts
  fetch 到 /coc/api/sessions/{id}/actions/stream
  ↓
api.py
  FastAPI 接收请求，调用 KeeperAgent.run_turn
  ↓
agent.py
  LangGraph 节点依次处理：读档、理解、检索、裁定、掷骰、叙事、校验、落库
  ↓
story_state.py / models.py / retrieval.py
  更新剧情状态、数据库和向量记忆
  ↓
api.py
  返回 NDJSON：chunk + final
  ↓
App.tsx
  显示守秘人叙事，刷新角色、线索、物品和剧情状态
```

你可以把整个项目理解为：

```text
一个 Web 页面
  + 一组 FastAPI 接口
  + 一个 LangGraph 守秘人流程
  + PostgreSQL 存档
  + Chroma 资料检索
  + LLM 叙事生成
```
