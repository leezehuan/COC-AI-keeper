# coc-lite 后端主线精读

> 这份文档专门服务一种阅读目标：  
> **你想知道“玩家在前端输入一句话之后，后端到底按什么顺序处理，最后又把什么写进数据库”。**

---

## 1. 先抓住一条主线

如果你现在刚学 Agent 项目，不要试图一口气读懂所有文件。  
先只记住下面这一条链路：

```text
前端 App.tsx
  -> frontend/src/api.ts
  -> backend/app/api.py
  -> KeeperSupervisor.run_turn()
  -> ContextAgent
  -> PlannerAgent
  -> ExecutorAgent
  -> NarratorAgent
  -> GuardAgent
  -> KeeperSupervisor._commit_state()
  -> build_action_response()
  -> 前端渲染
```

这条链路就是项目的“主干”。  
你第一次读代码时，只要能把这条主干走通，后面再看 Tools、Skills、RAG、提示词，就会轻松很多。

---

## 2. 每一层到底做什么

### 2.1 `frontend/src/App.tsx`

它负责两件大事：

1. 收集玩家输入  
2. 把后端返回的数据显示出来

比如玩家点击一个选项，或者在输入框里输入：

```text
我划向北岸码头，检查附近有没有脚印。
```

`App.tsx` 会调用 `api.streamAction()`，发起一个流式请求。

你可以把它理解成：

- `App.tsx` 决定“什么时候发请求”
- `api.ts` 决定“请求怎么发”

---

### 2.2 `frontend/src/api.ts`

这是前端的 API 封装层。

重点看两个函数：

- `request()`：普通 JSON 请求
- `streamRequest()`：流式 NDJSON 请求

这里最值得学习的是 `streamRequest()`。

因为它展示了一个很常见的前后端模式：

```text
后端一边生成结果
前端一边读取结果
页面一边更新结果
```

也就是说，玩家不必等整段叙事生成完，页面就能先看到一小段一小段文字。

---

### 2.3 `backend/app/api.py`

这是后端 HTTP 接口层。

它不负责“复杂推理”，而负责“接请求”和“回响应”。

对于主回合来说，最重要的是这个接口：

```python
@router.post("/sessions/{session_id}/actions/stream")
def submit_action_stream(...)
```

这个函数做了三件事：

1. 检查会话是否存在
2. 在后台线程里调用 `get_agent().run_turn(...)`
3. 把执行过程包装成 NDJSON 事件流返回给前端

### 为什么要开线程？

因为守秘人回合比较重：

- 要查数据库
- 要查向量库
- 要调 LLM
- 还可能要生成图片

如果不单独处理，流式返回会比较僵硬。  
这里用 `Queue + Thread` 的方式，把“Agent 执行”和“事件输出”解耦了。

---

## 3. `KeeperSupervisor` 为什么是核心

文件：`backend/app/services/agents/supervisor.py`

如果你只选一个后端文件精读，那就是它。

因为它是“总调度器”，负责把五个 Agent 串起来。

你可以把它理解成：

- `api.py` 像前台接待
- `KeeperSupervisor` 像总导演
- 5 个子 Agent 像不同工种的专业成员

---

## 4. 一次回合的 6 个阶段

`run_turn()` 基本可以按下面的顺序理解：

### Phase 1. `ContextAgent`

负责准备原材料。

它会：

- 从 PostgreSQL 读取会话、角色、线索、物品、回合日志
- 解析玩家意图
- 从 Chroma 检索剧本、规则、实体、记忆
- 组装 `visible_context` 和 `keeper_only_context`

一句话：

> 它回答的是“现在是什么情况，以及玩家大概想干什么？”

---

### Phase 2. `PlannerAgent`

负责先做计划，再执行。

它会生成：

- 本回合目标
- 允许调用哪些 Tool
- 允许调用哪些 Skill
- 风险等级
- 是否需要追问玩家

一句话：

> 它回答的是“这回合理论上应该怎么处理？”

---

### Phase 3. `ExecutorAgent`

负责真正执行。

它会：

- 运行 Skill
- 收集 Tool 观察结果
- 执行规则裁定
- 必要时掷骰
- 汇总成 `resolution`

一句话：

> 它回答的是“按计划执行后，实际上发生了什么？”

---

### Phase 4. `NarratorAgent`

负责把“结果”翻译成“玩家能看到的叙事”。

它会生成：

- `narration`
- `options`
- `state_delta`

注意这里一个非常重要的设计：

`NarratorAgent` 不只产出文本，还产出结构化状态增量。  
这意味着项目不是只靠“故事文本”推进，而是靠“文本 + 结构化状态”一起推进。

---

### Phase 5. `GuardAgent`

这是最后一道防线。

它会做：

1. 确定性校验
2. Reflection 自检
3. 防剧透清洗
4. 修复判断

如果它发现问题，Supervisor 会进入 repair loop。

这个设计很值得学习，因为它说明了一个现实问题：

> 让 LLM 直接生成最终答案通常不够稳，需要一个“审稿层”。

---

### Phase 6. `_commit_state()`

这是初学者很容易忽略、但其实最重要的一步。

前面 5 个阶段都更像“思考”和“生成”，  
只有这里真正让游戏世界发生长期变化。

它会：

1. 更新角色理智值
2. 合并 `state_delta`
3. 更新 `session.current_location/current_scene/current_time`
4. 新增线索
5. 应用物品变化
6. 更新摘要
7. 写 `TurnLog`
8. 写入会话记忆到 Chroma
9. `db.commit()`

一句话：

> 前面的 Agent 负责“决定发生什么”，`_commit_state()` 负责“真的记下来”。

---

## 5. 为什么 `state_delta` 很关键

如果你刚接触这类项目，很容易只盯着 `narration` 看。

但从工程角度看，更关键的是 `state_delta`。

因为叙事文本是给人看的，结构化状态才是给程序继续运行用的。

例如一个回合结束后，文本里可能写：

```text
你登上了北岸码头，发现木板上有新鲜脚印。
```

但程序真正依赖的是类似这样的数据：

```python
{
  "location": "北岸码头",
  "time_cost_minutes": 10,
  "danger_delta": 1,
  "generated_clues": [...],
  "scene_updates": {...},
  "story_updates": {...}
}
```

后续系统能否正确记住地点变化、时间推进、线索发现，主要看这个结构，而不是只看那句叙事。

## 6. `story_state.py` 在整条链路里的位置

文件：`backend/app/services/story_state.py`

它可以理解成“长期剧情状态的维护器”。

建议重点理解三个函数：

### `ensure_story_state()`

作用：补齐状态结构。  
避免旧存档、空存档因为字段缺失而报错。

### `build_turn_delta()`

作用：把当前回合变化整理成统一格式。

这一步像“把自由文本整理成标准表格”。

### `apply_turn_delta()`

作用：把本回合变化真正合并到长期状态里。

这一步像“把本次修改写回存档”。

## 7. 为什么同时有 PostgreSQL 和 Chroma

这是另一个很适合初学者建立直觉的点。

### PostgreSQL

负责保存“结构化、确定性、长期存在”的数据：

- 角色
- 会话
- 线索
- 物品
- 回合日志
- 当前状态

### Chroma

负责保存“便于语义检索”的文本向量：

- 剧本分块
- 规则分块
- 结构化实体文本化后的片段
- 会话摘要和长期记忆

你可以先粗略地记成：

```text
PostgreSQL = 存档
Chroma      = 搜索用记忆库
```

## 8. 读代码时推荐盯住哪些变量

如果你怕在代码里迷路，可以优先追下面这些变量：

- `player_input`
- `intent`
- `turn_plan`
- `react_trace`
- `resolution`
- `narration`
- `options`
- `state_delta`
- `story_state`
- `session.state`

这几个变量几乎串起了整条后端主线。

### 推荐追踪法

当你打开一个文件时，优先问自己：

1. 这个文件是“读这些变量”，还是“写这些变量”？
2. 它改动的是临时数据，还是长期状态？
3. 它是在生成文本，还是在维护结构化状态？

这三个问题会帮你很快定位文件职责。

## 9. 很适合做的 4 个练习

如果你是学生，我很推荐你边读边做下面这些小练习。

### 练习 1：追一次主回合

选一句输入：

```text
我检查灯塔门口有没有拖拽痕迹。
```

然后依次追：

- 前端是哪个函数发请求
- 后端是哪个 API 收到请求
- `run_turn()` 先调了哪个 Agent
- `state_delta` 最后写了什么

---

### 练习 2：打印 `turn_plan`

在 `PlannerAgent.run()` 里观察：

- `intent` 是什么
- 生成的 `allowed_tools` 是什么
- 生成的 `allowed_skills` 是什么

这个练习特别适合理解“计划层”和“执行层”的分工。

---

### 练习 3：只看一次 `_commit_state()`

不要急着看所有 Agent，先只精读 `_commit_state()`。

你的目标是回答：

> 一回合结束后，哪些数据被永久保存了？

如果这题你能答清楚，说明你已经比很多初学者更接近“工程视角”了。

---

### 练习 4：对照前端 `types.ts`

看看后端返回的字段，最后在前端分别落到了哪里：

- `narration`
- `options`
- `state_delta`
- `discovered_clues`
- `image_url`

这个练习能帮你打通“后端返回什么”和“页面显示什么”之间的关系。

## 11. 一句总总结

这个项目最值得你学习的，不只是“怎么调 LLM”，而是：

> 如何把“自然语言输入”变成“结构化计划、结构化执行、结构化状态、结构化持久化”。

这是 Agent 工程和普通 Demo 最大的区别之一。
